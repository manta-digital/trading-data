# Slice 912 — Production verification on `.144` (task 6.2)

Success criterion 1 verified against production data on 2026-08-03, after
promoting `trading-data-maintenance` to `main` and updating the host checkout to
v0.7.4.

## Method

`mt data daemon run --daily --stop-when-done`, interrupted with Ctrl-C partway
through the pass, then re-invoked. The second invocation is a fresh process, so
it carries no in-memory state from the first — which is the point: under the
pre-912 behavior the restart re-ran the whole universe, and that is what made
the underlying defect invisible.

## Result

| | Pending | Note |
|---|---|---|
| Run 1 start | 11,976 | 12,882 scope − 906 unactionable |
| Run 1 exit (interrupted) | 11,859 remaining | 117 symbols processed |
| Run 2 start | **11,859** | exact match |

`11,976 − 117 = 11,859`, and run 2 opened at exactly 11,859. The resume set is
precisely the symbols the interrupted pass never reached — no overlap, nothing
re-fetched, nothing skipped.

## What this confirms

- **Criterion 1.** An interrupted daily pass resumes at the unreached symbols
  within the same UTC day, and a process restart neither loses work nor repeats
  it. Under pre-912 behavior run 2 would have been handed all 11,976 again.
- **D1.** The resume set derives from `acquisition_state.last_attempt_ts`
  correctly against real data at full scope, not just against the mocked and
  simulated cases in the unit suite.
- **D6 / issue #4.** 906 unactionable symbols reported, matching issue #4's
  count exactly by an independent route.
- **D4.** An earlier run the same day, with the pass already complete, exited
  reporting "no actionable work in scope" and made no provider call — the
  drained path, distinct from the closed-gate path that issue #6 was about.

## Cost

Each run issues one bulk EOD call in STEADY_STATE mode, so the interrupt-resume
test cost 200 credits against the 100,000/day quota.
