## 9.5 — induced staleness: the guard fires (criterion 7)

Method: throwaway DB (`mt_stale_8401f880331d`) → full migration chain → seed
3 symbols (ZZSTALE1-3, minute+daily/daily-only/empty) with 2010 bars →
NULL-bounds refresh (R2a), parent before child. Every verdict read goes
through the real accessor (`query_data_status`) with the TTL cache reset, so
each read re-probes. Each signal induced independently, others quiescent,
with a restore-to-fresh check after each. Script: session scratchpad
`induce_staleness.py`; **13/13 steps passed**.

| step | induction | observed |
|---|---|---|
| A0 | seeded raw, caggs never materialized | STALE, `LAG_EXCEEDS_THRESHOLD` (empty cagg = maximal lag, not fresh-by-default); rows still returned (D3a) |
| A1 | materialize manually; policies have **never run** (`job_stats` NULL) | FRESH — no false staleness on never-run policies (9.6) |
| B | pause `minute_coverage` policy (catalog `scheduled=false` — see finding below) | STALE, exactly `NOT_SCHEDULED`; rows still returned; fresh again on resume |
| C | insert one minute bar at `now()` into a newer year-bucket, no refresh | STALE, exactly `LAG_EXCEEDS_THRESHOLD`; **lag=5840d judged against threshold 1d4h** — the D4 case: the ceiling caps the deliberately loose 750d `start_offset`, which alone would have called this fresh. Fresh again after parent-then-child refresh |
| D0 | `CALL run_job()` — genuine policy run | FRESH, real Success row in `job_stats` |
| D | flip that row's `last_run_success` to false | STALE, exactly `LAST_RUN_FAILED` (a `scheduled`-only check calls this healthy) |
| E | set `last_successful_finish = now() - 3d` (scheduled, "succeeding") | STALE, exactly `LAST_SUCCESS_TOO_OLD`; fresh after restore |
| F | re-pause, run real `mt data status` subprocess against throwaway DB | banner (`OUT OF DATE`) rendered above tables, exit 0, rows rendered; `--json` → `coverage.is_stale: true`; banner absent after resume |

D and E flip single fields on the *genuine* job-stats row created by D0 —
the catalog values are the signal inputs, and a 25-hour wait is the only
non-catalog way to age `last_successful_finish`.

### Operational finding: `alter_job` cannot pause the hierarchical coverage cagg

`SELECT alter_job(<job>, scheduled => false)` — the runbook's standard
pause/resume mechanism — **fails on `minute_coverage`'s refresh policy** with
`multiple refresh policies are not supported for hierarchical continuous
aggregates` (TimescaleDB re-validates policy config on alter; measured, both
bound-param and literal forms; `daily_coverage`'s policy alters fine).
Pause/resume for `minute_coverage` must go through the job catalog:
`UPDATE _timescaledb_config.bgw_job SET scheduled = false|true WHERE id =
<job>`, which is exactly what `timescaledb_information.jobs` (the guard's
input) reads. Runbook amended (R2b).
