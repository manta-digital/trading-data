### Finding: leftover test roles in production's catalog

`t913_app_29b4ce5b85` and `t913_mig_29b4ce5b85` are **residue from an
interrupted test run**, sitting in production's shared `pg_authid`.

`test/integration/data/test_role_privileges.py:73-125` creates a per-run pair of
throwaway roles named `t913_app_<10 hex>` / `t913_mig_<10 hex>` and drops them in
the fixture's `finally` block. A run that dies between provisioning and teardown
leaves the pair behind, and nothing sweeps them afterwards. Two are present now.

This is live evidence for the slice's second stated cost — roles are cluster-wide,
so a test run writes into the catalog production depends on — and it is exactly
the class of residue that disappears once the test cluster is separate.

## Task-ordering correction required before F.6

**A.1's snapshot cannot serve as the baseline for success criterion 4 as the task
file currently orders the work.** A.3 runs the integration tier against the
shared cluster, and that run creates and drops its own `t913_*` role pair — so the
role set legitimately changes between A.1 and A.3 through no action of this slice.
Comparing F.6 against the A.1 snapshot would fail for a reason unrelated to 917.

The correction, to be applied to the task file before Group F:

1. Keep the A.1 snapshot. It is the evidence above, and it records the
   pre-existing residue.
2. **Re-capture the role set after A.3 completes.** That second snapshot is the
   authoritative baseline for F.6.
3. F.6 compares the **persistent** role set — excluding `t913_*` — and separately
   asserts that no *new* `t913_*` residue was introduced. Filtering that prefix as
   transient is an existing project convention, not a new one:
   `test/integration/data/test_test_admin_role.py:87` already does
   `{m for m in memberships if not m.startswith("t913_")}` for the same reason.

Dropping the two stale roles is **not** part of this slice. They are production
catalog objects, and removing them is a Project Manager decision.
