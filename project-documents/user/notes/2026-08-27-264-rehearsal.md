## Step 3 — the rule, inspected before it runs (Criterion 2 ✅)

`mt data kalshi status --json | jq .candles.rule` — the shipped defaults:

```json
{"traded_only": true, "categories": [], "excluded_categories": ["Mentions", "Sports"],
 "excluded_series_pattern": "MENTION|SAY",
 "excluded_title_pattern": "\\m(say|says|mention|mentions)\\M",
 "description": "traded 24h · categories all · excluding Mentions, Sports · patterns 2"}
```

**An env override moves the report with no collection at all:**

| rule in force | `selected_open` | `closed_excluded_by_rule` |
|---|---|---|
| default (rule C) | 7,335 | 32,260 |
| `MT_KALSHI_CANDLE_CATEGORIES=Sports`, exclusions cleared | **11,162** | 28,142 |
| default again | 7,335 | 32,260 |

`market_candle_state` held 9,620 rows before and after — the numbers moved
because the *rule in force* changed, not because anything was collected.

The hand-spelled predicate of the walkthrough (categories + both patterns +
`volume_24h_fp > 0`) counted **7,307** live selected markets against the
repository's 7,335 at the same moment; the small gap is the 24 h volume window
moving between the two queries, not a predicate disagreement.

**Uncategorised series: 0 of 13,545** had a NULL `category` or NULL `title` in
this snapshot. The NULL-handling fix (review F003) is therefore *not*
exercised by production data today — it remains proven by the integration
test's sixth fixture market, and it is what keeps a future uncategorised
series from being silently dropped.

### Every series the exclusion patterns match (410 rows) — read in full

Category breakdown: **Mentions 402 · Entertainment 3 · Politics 2 ·
Economics 1**. The eight matches outside the `Mentions` category are exactly
what the patterns exist for (188 mention-series live elsewhere, per Discovery
Findings) — **with one over-reach worth recording**:

- `KXNWSAYLOR` — *"Michael Saylor net worth on [date]"*, category Economics.
  The ticker regex `MENTION|SAY` matches the **"SAY" inside "SAYLOR"**. This
  is a genuine false positive: a Michael-Saylor net-worth market is not a
  mention market. It is one series and its markets are simply not collected.
  Left as-is for this slice (the rule is configuration — an operator who wants
  it can set `MT_KALSHI_CANDLE_EXCLUDED_SERIES_PATTERN=MENTION|\\mSAY` or
  similar); recorded here so the next person does not rediscover it as a bug.

### Compression (Criterion 13 — policy verified; no eligible chunk here)

**The walkthrough's own SQL is wrong and must be corrected in the design:**

```
call run_job((select job_id from timescaledb_information.jobs where …));
ERROR:  cannot use subquery in CALL argument
```

PostgreSQL does not accept a subquery as a `CALL` argument. Resolve the id
first, then call with the literal — still by hypertable name and `proc_name`,
never a recorded id:

```sql
select job_id from timescaledb_information.jobs
 where proc_name='policy_compression' and hypertable_schema='kalshi'
   and hypertable_name='candlesticks';        -- → 1000 (regenerates; never record it)
call run_job(1000);                            -- → CALL
```

The job ran clean (`last_run_status = Success`, `total_failures 0`) and the
policy is still `scheduled = t` with `compress_after = 336:00:00` (14 days).
**Nothing compressed, correctly:** both chunks
(`2026-08-19 → 08-26`, `2026-08-26 → 09-02`) are newer than the 14-day
horizon, because this rehearsal only ever collected recent candles. Compression
of a genuinely old chunk — and rows reading back identical afterwards — is
proven by the integration test
`test_kalshi_candles.py::TestCompression::test_policy_compresses_an_old_chunk_and_rows_survive`,
which creates rows past the horizon on purpose.

## Pending queries' wall time (design *Special Considerations*; review F007)

Measured against the rehearsal catalog (188,798 markets, `kalshi.markets`
549 MB; `kalshi.candlesticks` 360 MB / 1.54 M rows):

| query | wall time | rows |
|---|---|---|
| `pending_live` | **70 ms** | 7,021 |
| `pending_finishing` | 10 ms | 0 |
| `pending_backlog` (limit 100,000) | 28 ms | 0 |
| `count_backlog_remaining` | 22 ms | 0 |
| `count_behind_cutoff` | 7 ms | 0 |

All five are well under a tenth of a second on a catalog of this size. The
design named a partial index on `markets (settlement_ts) WHERE status =
'finalized'` as the first lever if the backlog query dominated — **it does
not**, so no index is added. Production's catalog is ~3.5 M markets (~18×);
even at linear scaling `pending_live` would be ~1.3 s against a phase that
runs for minutes, so this stays a non-issue. Re-measure if the phase's own
wall time ever looks query-bound.

## Deviations from the walkthrough as written

1. **`call run_job((select …))` does not work** — corrected above; the design's
   step 5 must be updated (Task 8.4).
2. **The `\timing on` bullet** was satisfied by timing the repository methods
   directly in-process rather than through `psql`, which measures the exact
   statements the phase issues (including their bind parameters) instead of a
   hand-retyped approximation.
3. **`--settled-since 6 hours`** kept the catalog to ~189 k markets as the task
   directed; the backlog and behind-cutoff figures are therefore small and are
   not representative of production.
