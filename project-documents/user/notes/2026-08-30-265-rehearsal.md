# Slice 265 rehearsal — throwaway database on the test cluster

Walkthrough steps 1–6 of `user/slices/265-slice.public-trades-collection.md`,
run 2026-08-30 14:20 → 14:42 UTC against a UUID-named throwaway database
`mt_rehearsal_265_8db0f034` created on the test cluster from
`MT_TIMESCALE_TEST_URL`. The production URL never entered the shell or any
child environment: the driver ran from a scratch directory with no `.env`

end (section *Dropped*).

driver's log; every figure below is quoted from it. Times are UTC.

## What the rehearsal deliberately did not do

1. **The cutoff start.** Substituted by the hand-seeded watermark at
   `now − 3 h` (step 4); the first-run floor at the cutoff is proven on the
   host by part 2 Task 9.2 (the phase-start journal line shows cutoff,
   watermark and coverage floor equal).
2. **The abort inside a window** (walkthrough step 7). Proven by Task 6.1's
   integration case against a real database
   (`test_kalshi_pass.py::TestThreePhasePass::test_mid_window_abort_…`) and
   by part 1 Task 4.3b cases 6 and 12 at the unit tier; not re-run by hand.
3. **The day-later late-arrival diff** named in the design's Risk
   Assessment. A task cannot wait a day; the in-session re-walk diff (step
   5: 0 rows) is the weaker substitute, and the residual risk is carried by
   the PM's drain observation.

## Deviations from the walkthrough's drafts, for the design

- The duplicate self-join `… where a.ctid <> b.ctid` fails on a compressed
  chunk (`transparent decompression only supports tableoid system column`);
  the walkthrough now uses `GROUP BY … HAVING count(*) > 1`, which returned
  0 before and after compression.
- The rule-description check in step 3 must run after a pass — before the
  candle phase has ever run, `.candles` is `null` by design.
- The `mt` CLI renders the rename guard as a Rich traceback ending in the
  message above, as it does every `Settings` failure; the exit code is 1.
