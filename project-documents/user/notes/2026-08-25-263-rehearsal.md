# 263 rehearsal — `mt data kalshi pass` on a throwaway database

Walkthrough step 1 of the slice design, run against the **test cluster**
(runbook 400 pattern). `MT_TIMESCALE_DB_URL` pointed at the throwaway
database for these commands only; the production URL was never present in
the shell (`env -u MT_TIMESCALE_DB_URL` on the setup step, and the value
passed explicitly per command thereafter).

## Setup

```bash
# throwaway database on the test cluster, kalshi track applied
CREATE DATABASE mt_263_rehearse_45d276d4
apply_migrations(pool, TRACKS["kalshi"])
```

This is a **cold catalog**: the settled stream drains from Kalshi's
historical cutoff (2026-06-26), which the design predicts runs long once.
That is the expensive case on purpose — a steady-state pass walks one window.

## Pass 2 — steady state, `--json`

```bash
uv run mt data kalshi pass --json
```

```
phases[].name: ['catalog']     outcome: ok     exit_code: 0
keys: duration_ms exit_code outcome phases run_id started_at
written per phase: series 220 · markets 38,172 · events 357 · settled 3,038 · awaiting 202
windows: 1     duration_ms: 97,159
```

This is the walkthrough's `jq '.phases[].name, .outcome, .exit_code'` check:
`"catalog"`, `"ok"`, `0`. Two things worth stating:

- **`windows: 1`, not 244.** The watermark persisted, so the second pass
  walked only the window that opened since. That is the write-on-change and
  resume property, measured rather than asserted.
- **97 seconds, against 45.7 minutes cold.** Within the design's 2–3 minute
  steady-state estimate (Decision 4), on a database holding 3.5M settlements.
  The writes are live churn on a venue running 15-minute ladders across a
  96-minute gap, not re-writes.

## Event stream (Criterion 4)

`jq -r .event_type` over the events file, in order:

```
pass_started run_started phase_finished(series) phase_finished(markets)
phase_finished(events) …
```

`pass_started` and `run_started` carry `phase: null`; the `phase_finished`
events name the sync phase. **One `run_id` across every event** — the pass
mints it and hands it to the catalog phase, so an events file for a pass
reads as a single run.

## Lock interaction (Criterion 2, lock case)

With a pass running in one shell, from a second shell:

```
$ uv run mt data kalshi sync
Error: another kalshi sync holds the run lock          # exit 1
$ uv run mt data kalshi pass
Error: another kalshi sync holds the run lock          # exit 1
```

Both commands take the same session-level advisory lock, so `pass` and
`sync` are mutually exclusive in both directions — a timer firing during a
hand-run sync exits 1 and the next firing succeeds, which is the intended
behavior, not a defect.

## Caveats worth carrying to the host

- A cold pass is **not** a 2–3 minute run: this one took **45.7 minutes**
  and captured 3.5M settlements across 244 windows.
  `TimeoutStartSec=infinity` on the service exists for exactly this — the
  90 s systemd default would have killed it in the first minute. On
  manta9000 the first drain is done by hand before the timer is enabled
  (walkthrough step 4's precondition), so the timer never meets this case.
- `last_full_sync_at` stays `NULL` for the whole drain and is written only
  when the run completes, while the watermark advances per window. That
  ordering is what makes an interrupted pass resumable rather than
  restart-from-zero — observed directly here mid-run.
- `--events-file` is a hand-run tool. Under the unit, `PrivateTmp=true`
  means the path named is not the path written; the journal is the
  supervised run's event log.
