# Slice Plan: Kalshi Event-Contract Data

## Parent Document

260-arch.kalshi-event-contract-data.md — Continuous collection of Kalshi prediction-market data: relational catalog (series → events → markets) with settlement capture, plus candlesticks and public trades, run as a bounded pass under the 916 supervised-production model.

## Foundation Work

1. [x] **(261) Kalshi Provider Foundation** — Register the provider: `ProviderType.KALSHI`, `ProviderProfile` with `AuthType.NONE`. Build the `trade-api/v2` API client: httpx-based, configurable rate limiter (shared-budget discipline per existing providers), cursor pagination, error taxonomy distinguishing transient from permanent failures, optional authenticated mode (RSA-PSS request signing; PM account exists and authenticated operation is planned near-term — public mode remains the required fallback), recorded real-response fixtures for every consumed endpoint. Verify Kalshi's current endpoint surface and the `/historical/*` cutoff behavior against published documentation (arch requires discovery, not assumption) and record findings in the slice design. Create the `kalshi` migration track on the TimescaleDB host with catalog tables (series, events, markets with lifecycle status and settlement fields) and collection-state tables (per-surface watermarks, awaiting-settlement set). Verifiable via client unit tests against fixtures and an applied/rolled-back migration on a throwaway database. Effort: 3/5

## Feature Slices

2. [x] **(262) Catalog Sync with Settlement Capture** — One-shot CLI command that syncs the catalog: discovers/refreshes series, events, and markets; tracks lifecycle transitions; maintains the awaiting-settlement set from close events and captures outcomes until settlement is recorded. Implements the incremental-vs-full sync strategy (the main algorithmic decision deferred by the arch; the binding constraint: no market may reach settlement unobserved). Idempotent upserts on ticker, persisted watermarks, structured events per the 120 pattern. First cut of `mt data kalshi status`: catalog watermarks, awaiting-settlement set with ages, lifecycle counts. Dependencies: [261]. Effort: 4/5

3. [x] **(263) Collection Pass and Supervised Install** — The bounded pass command (`mt data kalshi pass` or as finalized in design) composing collection phases in order — catalog only at this point — exiting nonzero on failure. Production wiring per 916: `mt-kalshi-pass.service` (oneshot, `Slice=manta-acquisition.slice`) + `.timer`, `install-production.sh` integration, `mt-run` wrapper verb (`sudo mt-run kalshi`, `mt-run status` row, `mt-run follow kalshi`), runbook section. Timer interval chosen for short steady-state passes; first-run catch-up simply runs long once. From this slice on, catalog and settlement data accumulate in production unattended — the initiative's time-sensitive value starts here. Dependencies: [262]. Effort: 2/5

4. [x] **(264) Candlestick Collection** — Candle phase added to the pass: per-market watermarked acquisition from market open through close, against the post-sync market set. Resolves the period-selection trade-off (finest-and-derive vs multiple periods); schema keys candles on `(market_ticker, period, timestamp)` with conflict-ignore. Extends `mt data kalshi status` with candle coverage: markets whose candles fall short of close, per the completeness definition. Dependencies: [263]. Effort: 3/5

5. [x] **(265) Public Trades Collection** — Trades phase added to the pass: cursor-driven trade tape, idempotent on Kalshi's trade id. Extends status with trade-cursor watermark and per-market tape completeness through close. Independent of 264 — the two phases can land in either order. Dependencies: [263]. Effort: 2/5

6. [x] **(267) Historical Backfill Phase** — [267-slice.historical-backfill-phase.md](../slices/267-slice.historical-backfill-phase.md) — A fourth phase of the hourly Kalshi pass drains `/historical/trades` backward from the live coverage floor to a ratified floor constant, and fetches candles for the behind-cutoff market set, under its own request cap (30 minutes of the rate budget ≈ 30,000/pass, authenticated with the PM's key) after the live phases, having first walked `GET /historical/markets` into the catalog once so the archived markets' trades classify instead of dropping as unknown. Starts on the first firing after install; no operator step beyond the key already on the host, no waiting on the live drain; progress and the floor are visible in `status`. Replaces the retired 266. Dependencies: [264, 265]. Effort: 3/5

## Notes

- Sequencing is driven by the initiative's time-sensitivity: 261 → 262 → 263 is the shortest path to unattended production accumulation of the catalog and settlement record. Candles (264) and trades (265) then extend the running pass; each addition redeploys via the normal pinned-ref update.
- Slice 266 (operator-run Historical Backfill, gated on the live drain finishing) was removed by the Project Manager on 2026-08-31 and replaced by 267, which runs the same backfill as a fourth pass phase with no wait.
- 264 and 265 are mutually independent. If prioritizing between them, trades are the surface Kalshi is actively migrating behind the historical cutoff.
- Potential for 263 (notes only, not yet needed — 262 rehearsal and first production run, 2026-08-25):
  - Log each completed settled window's end boundary at INFO (with fetched/written for the window) so an interrupted *replay* (`--settled-since` behind the watermark, which by design never moves the watermark backwards) shows an operator where it stopped, and so the long first-run drain has a progress line on the terminal. Today the remedy is to re-issue the same `--settled-since` (re-walked windows cost no writes) and to watch `mt data kalshi status` / the events file from another shell.
  - The first production run drew 429s on `/events` only (each recovered on retry 1/4, ~1 s backoff) during the markets walk's parent resolution at the 300/min public budget; `/markets` pages did not. Kalshi's unauthenticated limit appears tighter or per-endpoint for `/events`. Levers already available: `MT_KALSHI_REQUESTS_PER_MINUTE` (lower the budget) or authenticated mode (higher documented budget). Worth deciding a production budget for the timer in 263.
- Decisions the architecture explicitly defers to slice design: incremental-sync strategy and cadence (262), candle period selection (264), awaiting-settlement stuck threshold (262 — the age visibility itself is required, only the threshold is open), timer interval (263), exact CLI command names (262/263).
- PM direction for 264's period decision (20260824): minute resolution is the analytically required granularity — Kalshi probability spikes play out on the order of minutes, and those are what future analysis needs. 264 still owns the trade-off's mechanics (which periods to fetch/store), but a design that cannot deliver 1-minute candles does not satisfy the requirement.
- 265's trade table keys on `(market_ticker, created_time, trade_id UUID)` — composite, containing the time column (TimescaleDB requires unique constraints to include the partition column), ticker first so per-market reads come off the primary key. **Revised at 265 design, PM-ratified 20260828**: the original note asked for `(created_time, trade_id)`; measurement showed ticker-first 13 B/row cheaper than time-first plus the per-market index it would need. `trade_id` stays globally unique so idempotency is unchanged; a time-only index is a later addition if exchange-wide range reads need it.
- No hypertable is created in this plan. Tables are plain relational on the TimescaleDB host; promotion is a future decision after observed volume, kept in-place-cheap by host placement (arch: Volume and storage posture). PM assessment (20260824): promotion is nearly certain eventually — especially for trades and minute candles — so growth should be watched rather than discovered; promoting at tens of millions of rows is cheap, at hundreds of millions it is a long maintenance window.
- Kalshi storage lives in the `kalshi` PostgreSQL schema on the shared `trading` database (261 design decision, PM-approved), with an expectation of eventual extraction to a dedicated database for zero blast-radius crossover with equities. Binding discipline on all slices: nothing in the `kalshi` schema may reference or join `public` tables, so extraction stays a dump/restore plus URL change.
- **262 prerequisite — apply the kalshi migration track to production before 262's first run (PM action, 20260824). DONE 20260824:** `kalshi_001_schema`, `kalshi_002_catalog`, `kalshi_003_collection_state` applied to production from the dev checkout via runbook 100; `status --track kalshi` reports 0 pending. Later kalshi migrations (262's `kalshi_004` onward) follow the same routine apply step. Original note: 261 delivered the `kalshi` track but deliberately did not apply it to production; the production ledger shows `kalshi_001_schema`, `kalshi_002_catalog`, `kalshi_003_collection_state` pending. It was rehearsed on the test cluster on top of a full minute-track ledger (runbook 100, *Update procedure* → migrations). 262's design must carry this as an explicit deployment step and its walkthrough must start with it: tag the release → runbook 100 update procedure → `uv run mt data migrate status --track kalshi` (pre-flight, application credential) → `uv run mt data migrate apply --track kalshi` (maintenance credential, interactive shell) → `status` again shows 0 pending → then the first catalog sync. Additive and idempotent; no down-migration exists.
- **MVE/parlay markets are out of scope for the initiative (PM decision 20260824, recorded against 262 design review F002).** Every markets request carries `mve_filter=exclude`; "no market may reach settlement unobserved" applies to the non-MVE catalog. The PM also accepted 262's measured storage figure (~70 GB/year in `kalshi.markets`, dominated by 15-minute crypto ladders) and directed that market selectivity — which markets get candles and trades — is a 264/265 decision informed by the populated catalog, not a catalog-level filter.
- The cross-source arbitration gap (916 deferred, names Kalshi as trigger) is inherited, not addressed here — it is a 916 follow-on slice outside this initiative. Mitigations in this plan are structural: bounded pass, sparse timer, conservative rate budget.
- Orderbook snapshots are deliberately absent: live-only data arguing for capture, but websocket-based streaming form and unresolved cadence/storage cost make it separately-scoped future work, not a slice here.

## Future Work

1. [ ] **Orderbook Snapshots** — Websocket-based streaming capture of orderbook depth for selected markets; `Type=simple` unit per the production-form ADR (journal 20260823), separate from the pass. Requires its own scoping decision on market selection, cadence, and storage. Dependencies: [262].

2. [x] **Authenticated Tier Adoption** — Superseded (20260824): folded into slice 261 as an optional client mode (RSA-PSS signing, mode-selected rate budgets) after the PM confirmed a funded, verified account and near-term intent. The architecture's constraint stands: the collector keeps working without credentials.

3. [ ] **Near-Real-Time Collection** — To execute strategies against Kalshi data live (the pass-collected historical record is for researching and testing them — journal 20260824), collection must move closer to real time than the sparse-timer pass provides. **Form decided (PM, 20260824): streaming — websocket subscriptions in a long-running `Type=simple` unit per the production-form ADR. Tight timer cadence is rejected**: an always-firing pass forces the two hard sub-gaps 916 deferred (priority/preemption between concurrent pass units, and timer stagger-packing, which a tight timer cannot participate in), whereas a streaming unit never enters pass scheduling and activates only the tractable one — real resource weights on `manta-acquisition.slice` plus DB write throughput, tuned from measured contention. Kalshi streaming will mature alongside realtime tick streaming (the prime end-state of data gathering, per the same journal entry); whichever is scoped second designs against measured contention from the first. Still requires its own scoping: market selection and latency target. Dependencies: [264, 265]. Related: Orderbook Snapshots (same streaming form; likely co-scoped).

4. [ ] **Hypertable Promotion** — If observed trade/candle volume warrants (PM assessment 20260824: nearly certain eventually), promote those tables to hypertables in place on the TimescaleDB host, with chunk intervals sized against wall-clock span per journal entry 20260719. The 265 composite trade key (see Notes) is the enabling precondition. Dependencies: [264, 265].
