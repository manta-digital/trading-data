# Slice Plan: Futures Historical Bars, Statistics and Tick Aggregation

## Parent Document

300-arch.futures-historical-bars-statistics-and-tick-aggregation.md — Deep bar history (`ohlcv-1m`), open interest and settlement (`statistics`), and contract definitions for ES and GC, stored as archive units in their own tables; the open-interest roll rule; one bars read path with a named source; completeness checks for every futures tier; serving; and a small real purchase that proves 220's purchase path. Tick-derived aggregates are conditional. Live capture is initiative 280.

Measured on 2026-10-28 (free metadata calls, usage-based list prices, `GLBX.MDP3` parent symbols, 2010-06-06 to 2026-10-15): ES and GC `ohlcv-1m` is $89.74, `statistics` $1.45, `definition` $2.72. Together $93.91, outside any subscription. `ohlcv-1s` is $1,111 and is not in this plan's slices.

## Foundation Work

1. [x] **(300) Archive Generalisation** — The archive, manifest and ingest stop assuming every schema is a tick tier. Schemas belong to families (tick tiers, bars, statistics, definitions); supersession applies within a family only, so a bar unit never supersedes a `tbbo` unit. Ingest selects its projector per schema from one registry instead of the single `tick_trade` writer, and the tier-plus-definition bundle stays a tick-tier rule. Each request row gains a plan-inclusion marker, set from one configuration table (schema to included history, from the Databento pricing page), and the 30-day spend guard counts marginal spend only; list-price estimates stay on the row for information. The `tick` track, `MT_TICK_*` settings and `mt data tick` names do not change. No new schema is added here, so the tick pipeline's behaviour is unchanged, which the existing tick tests and a parity run on the held files prove. Dependencies: none within this plan. Risk: Medium. Effort: 4/5

## Feature Slices (in implementation order)

2. [x] **(301) CME Calendar History** — Extends the `CME_EQUITY` and `CME_METALS` calendars back to 2010-06-06, the start of the Databento CME dataset, so a bar, statistics record or definition from 2010 to 2019 can be placed in a session. Regular hours become dated (`trading_calendar_hours`), because the Globex close moved during the period and a bar after the old close would otherwise fail ingest. Every pre-2020 holiday, early close and unscheduled closure is one sourced row citing a dated CME document, and nothing is generated from a holiday rule. 2020 onward is untouched, which a before-and-after comparison proves. Session open and close stay queryable per calendar and date, since later slices read them: the 1d bar is the CME session, intraday roll-ups are clipped to the session open, and the tick-bar count restarts at each session open. It buys nothing and changes no tier. Dependencies: none within this plan. Risk: Medium. Effort: 3/5

   Design inputs (settled in review of the first design, which was discarded):
   - Eras are searched for and entered only for 2010-06-06 to 2019-12-31. A documented hours change from 2020 on is recorded as a finding, not entered, because 2020 onward stays untouched.
   - The ES close moving from 16:15 CT to 16:00 CT around September 2015 is a forum lead, not a source. An era is entered only from a dated CME document; if none is found the fill stops there and says so.
   - A date before a calendar's first era is an explicit error naming the calendar and date, never a fallback to the `trading_calendars` hours.
   - `CME_DATASET_START = 2010-06-06` is a new constant. It is the first populated session date, so it moves later if an era cannot be sourced. The existing `*_SEED_START` constants stay at 2020-01-01, so the existing minute migration is unchanged on a fresh database.
   - The migration first checks that no CME holiday row and no CME session exists before the seed start, then inserts with a plain `INSERT` (no `ON CONFLICT DO NOTHING`), so a stored row can never silently win. It also compares sessions from 2020-01-01 on before and after.
   - The migration takes the next free primary id. Read the last id in `MINUTE_MIGRATIONS` rather than trusting a number written in a plan.
   - `scripts/verify_cme_sessions.py` accepts dates before 2020. NYSE and NASDAQ are unchanged.
   - Interfaces: 302, 303, 304, 305, 306 and 307 read the sessions this slice creates.

3. [x] **(302) ohlcv-1m and Definition History** — Adds `ohlcv-1m` and full-range `definition` as archive schemas, built and tested on the DBN project's sample files and the local files. Bars land in their own table keyed by contract identity (never `minute_ohlcv`, never `tick_trade`). `definition` back to 2010-06-06 is a prerequisite (301 supplies the pre-2020 sessions bars are placed in), since a bar record carries only an instrument identifier and contract identity comes through definition validity windows. Completeness ships with the tier: load-complete (unit verified, counts and first and last event time against the manifest) and the day-condition findings, in `mt data tick status` and `coverage`. The sparse-bar rule is applied: a quiet session is not a hole. Backup coverage of the new archive units is confirmed in this slice. Dependencies: [300, 301]. Risk: Medium. Effort: 4/5

   Design inputs (settled in review of the first design, which was discarded, and with the bar decisions of 2026-11-01):
   - `ohlcv-1m` is its own schema family (`BAR_1M`), named for its interval, so a later `ohlcv-1s` family cannot supersede it. Each interval gets its own table, with the same columns and projector, because `ohlcv-1s` is about 20 times larger (ES, all history: 8.7M 1m bars against 170.6M 1s bars) and needs its own chunk sizing. Rows are keyed `(instrument_id, ts_event)`, and `ts_event` is the bar open.
   - One bar ledger, `tick_bar_ledger`, covers every bar interval, reaching the interval through unit and request. Bar volume stays out of `tick_ingest_ledger` so the volume roll rule does not double-count. Before 2024 there are no ticks, so a volume-based roll rule over 2010 to 2023 can read only bar volume: the roll rule (303) must read `tick_bar_ledger` for bar-only ranges.
   - The universe gains history wants (`ohlcv-1m` and `definition`, each over its own range), validated at import. A bar range must lie inside the entry's `definition` range and start no earlier than `CME_DATASET_START`. A history want on an entry with `tier=None` is refused, because `tier=None` means "not chosen yet", not "no ticks wanted". A bars-only product needs an explicit no-ticks value, which the `ohlcv-1s` slice adds. Production configures no history wants here, so the pass plans exactly what it plans today.
   - A unit is load-complete when provider, decoded and stored counts agree and every bar's event time lies in the unit's UTC day. Status and coverage are per family, with the bar section headed "load-complete only", because content checks need statistics (303). A quiet session with few bars is complete. `coverage --schema ohlcv-1m` compares ledger to raw rows and exits 3 on a mismatch.
   - Nothing is bought. No provider `ohlcv-1m` file is held, so the code is built on the DBN project's sample files plus one real-shape bar day computed from a held `tbbo` day and marked "not purchased". 304 ingests the first real bar file.
   - `mt data tick estimate` gains an `ohlcv-1m` row judged on its own marginal cost. No API change here. Time bars are provider-only (journal ADR 20261101): 306 serves them and retires the read-time tick bars, and provider `ohlcv-1h` and `1d` are not archived here and never served.
   - Backup is mechanical: bar and definition files sit under the existing archive directory, both tables are in the tick database, `tick_bar_ledger` joins the restore drill's table set and `tick_ohlcv_1m` gets a fingerprint beside `tick_trade`'s, and the tick role privileges cover both tables.
   - Definition history: `tick_definition` grows by distinct instruments, so no capacity work. Pre-2020 records may carry an undefined activation or expiration. That fails its unit, naming the instrument, and is never patched with an invented window.

4. [x] **(303) Statistics and the Open-Interest Roll Rule** — Adds `statistics` as an archive schema with its own table. A statistics record is assigned to a session from its reference time and trading date, never its event time, and revisions are resolved by update action and receive time (both confirmed against the DBN statistics record definition). The tier's completeness ships with it, including the cross-tier check that a session's `ohlcv-1m` volume does not exceed `statistics` cleared volume (below it is normal). The open-interest roll rule is built on stored values and evaluated against calendar and volume for ES and GC, including the GC case where Databento's own continuous symbol differs from the volume rule. Dependencies: [300, 302]. Risk: Medium. Effort: 4/5

5. [x] **(304) First Real Purchase** — Runs 220's purchase path with real money for the first time, capped at $25 (PM, 2026-10-28). What it buys is kept and useful: `statistics` and `definition` for ES and GC over the full range (about $4), and the most recent years of ES `ohlcv-1m` with the rest of the cap. It goes through estimate, spend guard, manifest, batch download, verify and ingest, and the actual charge is compared with the estimate and the manifest. The slice's evidence is that comparison and the tiers' completeness verdicts on what was bought. Dependencies: [302, 303]. Risk: Low. Effort: 2/5

6. [ ] **(305) Futures Completeness Surfaces** — Brings tick, bar and statistics verdicts together in `mt data health`, `accounting`, `overview` and the status coverage aggregates, in place and not as a parallel set. The slice defines "source edge" and "caught up" for each futures tier, extends `COVERAGE_SOURCE_TABLE` and the status coverage logic beyond minute and daily, and adds the remaining cross-tier content check (`ohlcv-1s` summed to minutes against `ohlcv-1m` is wired but inactive until that schema exists). It also measures manifest-scale queries, preflight and status over tens of thousands of units, since history acquisition multiplies today's row count about a hundred times. Dependencies: [302, 303]. Risk: Medium. Effort: 3/5

7. [ ] **(306) Serving the New Tiers** — Bars through `/api/v1/futures/*` follow the architecture's source rule: provider `ohlcv-1m` is the default for 1m and every coarser bar, rolled up on the CME session model; ticks never produce served time bars, so today's read-time tick-derived bars are retired here and kept only as the parity check (journal 20261101 ADR); provider `ohlcv-1h` and `1d` are never served. Every response names its source. Open interest and settlement get routes, or an explicit recorded decision not to serve them. Documentation for humans and for agents is updated (`docs/api/reference.md`, `agents.md`, the OpenAPI file). Provider 1h/1d bucketing is checked at this slice's design and recorded. Dependencies: [302, 303]. Risk: Medium. Effort: 3/5

## Integration Work

8. [ ] **(307) Futures History Acquisition** — Takes the full range through the same pass: ES and GC `ohlcv-1m`, `statistics` and `definition` from 2010-06-08 (the first day the CME calendars cover; the sessions dated 2010-06-07 are not bought, 304 D1), whatever 304 did not already buy. 304 buys `statistics` and `definition` for both products over 2010-06-08 to 2026-11-01 and ES `ohlcv-1m` for calendar 2024 only, so 307's remainder is ES `ohlcv-1m` outside 2024, all of GC `ohlcv-1m`, and every want from 2026-11-01 to a fixed end of 2026-12-01. Measured on 2026-11-08 at list prices, that is about $89 outside a subscription, and the estimate and the guard print the real figure before any pull. Every unit is verified and ingested, the tiers' completeness verdicts and the cross-tier checks are run over the whole range, and the findings are recorded. Exit criterion: once the purchases are ingested, each family's not-caught-up count in `mt data health` is zero, or every remaining session is recorded by name with its reason. 305 reports not caught up as informational, so this criterion is what separates a real gap from work not yet done. Dependencies: [304, 305], and issue #69 (304's purchase compared with Databento's November invoice). Risk: Low. Effort: 2/5

9. [ ] **(308) Tick Bars and Compact Tick Serving** — Serves what ticks are for (journal 20261101 ADR). One incremental rollup module: one trade in, closed bars and the current partial bar out. One tick is one trade record, the count restarts at each session open, and the last bar of a session is kept and marked partial when it holds fewer than N trades (308 D2). It is checked against fixtures cut from real `tbbo` sessions, and history runs it in a loop with no SQL second implementation. A tick-bar route takes `ticks_per_bar` = any positive integer. Each bar carries open and close times, OHLC, volume, trade count, buy and sell volume by aggressor side, the bid/ask at close, and its identity (session date, index within session). Raw ticks move to a compact columnar encoding (integer nanosecond timestamps as deltas, integer prices, symbol and session once per segment) that carries trading-ui's display fields and the stream key (`ts_event`, `sequence`, `sequence_ordinal`) the live stream will reuse. The design answers how tick bars are admitted under the row ceiling when the bar count is not a function of the window. trading-ui's requirements are on issue #62. Documentation for humans and agents is updated. Dependencies: [306]. Risk: Medium. Effort: 3/5

## Notes

- **Order:** 300 is the foundation. 301 (calendar history) comes next because every schema from 2010 to 2019 needs its sessions. 302 and 303 follow in that order, since statistics needs the definitions and contract identity 302 builds. 304 comes before the large pull so the purchase path is proven on a small one. 305 and 306 depend only on 302 and 303 and can be taken in either order. 307 comes after 304 and 305, so everything it ingests can be verified. 308 needs only 306's serving shape, so it can be pulled ahead of 307 if the PM wants futures charts sooner; pulling it forward renumbers it.
- **Completeness with each tier:** the architecture's principle is that a tier ships with its completeness check, so 302 and 303 each carry their own. 305 is the cross-tier layer and the operator surfaces, not the first check.
- **No PM host steps:** no slice here needs a root step or a PM-run command, with one exception. In the purchase slices (304, 307) the PM sets the two spend ceilings with one root command (`deploy/set-tick-spend-ceilings.sh`), because runbook 100 reserves the ceilings to the PM. 307 prints that command with its values from the free estimate (307 D4).
- **Subscription:** none of these slices needs it. Every schema in scope is purchasable usage-based for under $100 in total, and the plan-inclusion marker makes a later subscription cost the guard nothing.
- **Backup:** the new archive units and tables join the tick backup regime in the slice that first writes them (302), as 220 did for ticks.
