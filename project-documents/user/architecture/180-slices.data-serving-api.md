# Slice Plan: Data Serving API

## Source

[180-arch.data-serving.md](180-arch.data-serving.md)

## Approach

Four slices. Skeleton first — FastAPI app wired to the DB, `mt serve` command, health endpoint — so we have a running server before adding any real endpoints. Bars second because it is the critical path for trading-ui and the most complex routing logic (minute vs. daily, date→datetime conversion, async/sync bridge). Symbols third, including the `available` ranges materialized view. Polish last: msgpack support, gaps endpoint, and OpenAPI cleanup.

Daemon and API server run as separate OS processes in separate terminals for now. Supervised launch (slice 155) is a future dependency; no work here. Redis/in-memory caching is similarly deferred — query latency is acceptable at current data volumes without it (future slice if profiling shows otherwise).

Each slice delivers a testable, operator-visible capability. The server does not need to be running for unit tests — all route handlers are tested via FastAPI's `TestClient`.

## Slices

1. [x] **(181) FastAPI skeleton + `mt serve` + health endpoint** — [181-slice.fastapi-skeleton-mt-serve-health-endpoint.md](../slices/181-slice.fastapi-skeleton-mt-serve-health-endpoint.md) — Add `fastapi`, `uvicorn[standard]`, `orjson`, and `msgpack` to `pyproject.toml`. Create `src/manta_trading/api/` package: `app.py` (FastAPI instance, CORS middleware allowing all local-network origins, lifespan hook that opens a psycopg3 connection pool from `Settings` on startup and closes it on shutdown), `deps.py` (dependency-injection helper that yields a `Connection` from the pool), `routes/health.py` (`GET /api/v1/health` — returns `{"status": "ok", "db": "ok"|"error"}`), `models/responses.py` (initial Pydantic models). Add `mt serve` Typer command in `src/manta_trading/cli/commands/serve.py` — wraps `uvicorn.run` with `--host`, `--port` (default `8100`), and `--reload` options. Register the command in the CLI app. This slice proves the server starts, connects to the DB, and returns a health response. No bar or symbol logic yet. Verifiable: `mt serve` starts without error; `curl http://localhost:8100/api/v1/health` returns `{"status": "ok", "db": "ok"}`; `curl http://localhost:8100/docs` returns the OpenAPI UI; unit test asserts health returns 200 with correct body; unit test asserts health returns DB error shape when pool is broken. Dependencies: [154]. Effort: 2/5.

2. [x] **(182) Bars endpoint** — [182-slice.bars-endpoint.md](../slices/182-slice.bars-endpoint.md) — Add `routes/bars.py`: `GET /api/v1/bars/{symbol}` with query params `granularity` (`Granularity` StrEnum from `manta_trading.constants`), `start` (ISO date), `end` (ISO date), `adjusted` (bool, default `true`), `format` (`"json"` | `"msgpack"`, default `"json"`). Route logic: define `_MINUTE_GRAINS = {M1, M5, M15, H1, H4}` in `bars.py`; convert `date` → `datetime` at midnight UTC before calling `TimescaleMinuteDataDB.get_minute_data(..., aggregation=granularity)`; call `TimescaleDailyDataDB.get_daily_data` for daily+ granularities. Both calls via `run_in_executor` (async/sync bridge). Serialize DataFrame to `BarsResponse` Pydantic model (fields: `symbol`, `granularity`, `adjusted`, `count`, `bars: list[BarRecord]`). Return orjson-serialized JSON by default; return msgpack bytes with `Content-Type: application/x-msgpack` when `format=msgpack`. Register 404 exception handler in `app.py` for empty result or unknown symbol. Verifiable: `GET /api/v1/bars/SPY?granularity=1d&start=2024-01-01&end=2024-01-31` returns correct OHLCV JSON with `count=21`; same request with `format=msgpack` returns binary with correct Content-Type; minute granularity routes to minute DB with datetime conversion; unknown symbol returns 404 `{"error": "..."}`; invalid granularity returns 422; `adjusted=false` returns unadjusted bars. Dependencies: [181]. Effort: 2/5.

3. [x] **(183) Symbols endpoints + `available` ranges view** — Add DB migration creating `symbol_data_ranges` materialized view: for each symbol and each granularity source table/aggregate, `MIN(bucket)` and `MAX(bucket)` partitioned by symbol. Add `pg_cron` or TimescaleDB refresh policy to refresh the view hourly (if available on the target DB); document manual refresh command as fallback. Add `routes/symbols.py`: `GET /api/v1/symbols` with optional `?search=` (prefix match on symbol) query param — returns array of `{symbol, name, exchange, type}` from `instruments` ordered by symbol. `GET /api/v1/symbols/{symbol}` — returns instrument metadata plus `available` dict from `symbol_data_ranges` view (granularities with no data are omitted). Register 404 for unknown symbol. Update `models/responses.py` with `SymbolSummary`, `SymbolDetail`, `SymbolsResponse`, `AvailableRange`. Verifiable: `GET /api/v1/symbols?search=SPY` returns SPY and any other SPY-prefixed symbols; `GET /api/v1/symbols/SPY` returns metadata with `available` block containing at least `1d` range; unknown symbol returns 404; `available` only includes granularities for which data exists. Dependencies: [182]. Effort: 2/5.

4. [x] **(184) Polish: gaps endpoint**, error handling hardening, OpenAPI cleanup — Add `routes/gaps.py`: `GET /api/v1/gaps/{symbol}` with `?granularity` and `?start`/`?end` query params — returns rows from `data_gaps` table for the symbol/granularity/window. Add consistent 500 exception handler in `app.py` that logs the full traceback at ERROR level and returns `{"error": "internal server error"}` (no SQL or stack trace in body). Audit all routes to confirm no DB errors leak detail to clients. Set FastAPI `title`, `description`, and `version` in `app.py` for clean OpenAPI docs. Suppress internal utility routes from docs if any. Add `--workers N` option to `mt serve` (default 1; documents single-worker rationale in help text). Note in `mt serve --help` that running alongside the daemon requires a separate terminal; reference slice 155 as the future supervised launcher. Verifiable: `GET /api/v1/gaps/SPY?granularity=1m&start=2024-01-01&end=2024-01-31` returns gap rows or empty list; injecting a DB error returns 500 with sanitized body and logs full traceback server-side; `GET /docs` shows clean API documentation with correct title/version; all four endpoints appear in the OpenAPI schema. Dependencies: [183]. Effort: 1/5.

5. [x] **(185) Staleness surface for API clients** — The serving API was built 2026-05-13/14 and predates the July 2026 data-quality era (slices 163/166/167/168) entirely; it has no freshness awareness. `GET /api/v1/bars` serves 5m/15m/1h/4h from the four minute caggs (`materialized_only=true`), so a stalled/paused refresh policy silently truncates the leading edge of bar responses with a 200 OK — the exact incident class slice 168 documented for the seeding path and slice 167 surfaced in `mt data status` (`OUT OF DATE` banner, `coverage.is_stale`). A client cannot distinguish "market closed" from "cagg stalled days ago." **Scope:** (1) `GET /api/v1/status` — expose the guarded `data_status` accessor (slice 167), including per-granularity-family coverage freshness verdicts; (2) a freshness field in `GET /api/v1/health` (e.g. `coverage: "ok"|"stale"`) so client liveness probes also catch serving-data staleness; (3) decide and implement a per-response staleness indicator on bars responses (header or body field) for cagg-served granularities. Reuse `assert_cagg_fresh` and the slice-167 accessors — no new freshness logic; the API only surfaces existing verdicts. Verifiable: with a coverage refresh policy paused on a disposable test DB (per `user/runbooks/cagg-maintenance-pausing.md`), `/api/v1/health` and `/api/v1/status` report stale and bars responses carry the indicator; with policies healthy, all report fresh; unit tests cover both states via mocked verdicts. Dependencies: [167, 168]. Risk: Low. Effort: 2/5.

6. [x] **(186) API client-contract hardening** — [186-slice.api-client-contract-hardening.md](../slices/186-slice.api-client-contract-hardening.md) — Pre-client contract cleanup; all items found in the 2026-07-31 API evaluation. **Scope:** (1) API pool session settings (`app.py::_configure_connection`): `statement_timeout` 300s → a value sized for interactive serving reads (post-163/166 all serving read paths are sub-second; target 15–30s), and revisit `work_mem = 512MB` × 8 pool connections (a 4 GB ceiling on the shared .144 host) — both values were copied from the bulk-analytics DB class, not sized for a client-facing API; (2) OpenAPI `version` read via `importlib.metadata` (currently hardcoded `"0.1.0"` while the package is 0.5.0), matching the CLI's existing pattern; (3) decide and implement the bars range-cap/pagination policy (a bare 20-year 1m request currently serializes unbounded rows through a single executor thread) and confirm-or-revise the 404-on-empty-window contract (client trap: 404 can mean "weekend", not "unknown symbol") — both decisions need client-team input before implementation; (4) commit a generated `openapi.json` as a reviewable artifact with a README/API-reference pointer, regenerated at slice close; (5) record the auth/CORS posture decision (currently no auth, `allow_origins=["*"]`; acceptable LAN-only) in the slice design as an explicit decision, not an omission. Verifiable: committed `openapi.json` matches the served schema; `/openapi.json` version matches the package version; tightened timeout demonstrated with an induced slow query; range-cap and empty-window behavior pinned by unit tests; decisions recorded in the design doc. Dependencies: [184]. Risk: Low. Effort: 2/5.

7. [x] **(187) Symbols ranges via coverage caggs + API load-test tier** — [187-slice.symbols-ranges-via-coverage-caggs-api-load-test-tier.md](../slices/187-slice.symbols-ranges-via-coverage-caggs-api-load-test-tier.md) — `GET /api/v1/symbols/{symbol}` computes `available` ranges via live per-symbol `MIN/MAX` at request time; slice 183 chose lazy queries over a matview and explicitly deferred a precomputed structure until ingest stabilized. Slice 167 has since built one: `minute_coverage`/`daily_coverage` (year-grain, `first_bucket`/`last_bucket`, ≤ ~22 rows per symbol, hourly refresh). **Phase 4 measurement corrected this entry's premise on three counts** (see D1/D5/D6): the expensive query is `daily_ohlcv` (2.5–4.0 s, 96% planning over 3,371 chunks), not the 5min cagg (32 ms); the coverage caggs are structurally stale on prod (`daily_coverage` 52 days behind, because a 365-day bucket is never refreshed until it completes); and `assert_cagg_fresh` cannot detect that, since it aligns the raw edge to the cagg's own bucket grid. **Scope:** (1) read `available` as a coverage floor merged with a *bounded* head probe — correct regardless of coverage staleness, and consulting no freshness verdict, so the guard-based fallback this entry originally specified is not what gets built; (2) give the coverage caggs a content-edge freshness check so their staleness stops being invisible, and pin the generic guard's one-bucket detection floor; (3) add the `test/load/` tier for `api_server` per the project Python rules, including a **request-latency** bound on bars — the gap `statement_timeout` structurally cannot close (186 D12b). CI gating for the tier belongs to slice 907 (`not_started`; the repo's only workflow is publish-on-tag), not here. Repairing the coverage refresh itself is a separate slice (PM, 2026-08-04). Verifiable: symbol-detail issues no unbounded aggregate (plan inspection); merged ranges equal the lazy result at date grain across a 20+ symbol sample; coverage reports stale against current prod data; load tests pass under the documented manual gate. Dependencies: [167, 185, 186]. Risk: Low. Effort: 3/5.

## Future Work 

1. [ ] **Response caching** (Redis or in-memory): defer until profiling identifies a bottleneck. At current data volumes and single-user access patterns, DB query latency is acceptable without caching.
2. [ ] **Background refresh of coverage freshness verdicts** ([issue #8](https://github.com/manta-digital/trading-data/issues/8)): `GET /api/v1/health` pays 3.19s on a cold verdict cache (0.010s warm) — measured on prod 2026-08-03 — because slice 185 D6 added two coverage probes to what was a bare `SELECT 1`. Cold hits occur on every server start and after any idle gap longer than the 60s TTL. Latency **accepted** by the PM 2026-08-03 with the operational requirement that liveness-probe timeouts be ≥5s; this entry tracks the structural fix. Seeding the cache during lifespan startup may remove most of the problem without a periodic task — measure that first. Scope to the two coverage caggs; the bars endpoint's per-granularity probes are inside their budget and should stay lazy.
3. [ ] **Representative disposable test DB**: a database with real cagg definitions and refresh policies over a small symbol/date subset — enough to induce and observe staleness end to end, without duplicating the ~4.4B-row production dataset. Surfaced by slice 185, whose induced-staleness verification (walkthrough step 7) could not run: prod is off-limits for pausing a refresh policy, and `trading_test` is unsuitable because its views are plain views, not caggs. Blocks end-to-end verification for 185 and any later slice that needs to exercise a stale-cagg path against something other than mocks. Decisions to resolve: how the caggs and policies are provisioned (migration replay vs. dump/restore of definitions only), which symbols and date span constitute "representative", and whether it lives on .144 or a local instance.

## Notes

- Slices 181 → 182 → 183 → 184 are a strict dependency chain. No slice can ship out of order.
- Slice 182 unblocks trading-ui development. Slices 183 and 184 can proceed in parallel with UI work once 182 is merged.
- Existing DB methods (`get_minute_data`, `get_daily_data`) are synchronous psycopg3. All API route handlers bridge to them via `run_in_executor`. Migrating to `AsyncConnection` is future work only if profiling shows contention at this access pattern.
- `Granularity` StrEnum lives in `manta_trading.constants` (confirmed). The minute/daily routing boundary mirrors the private `_MINUTE_GRAINS` set in `timescale_minute_db.py`; `bars.py` redeclares it as a module-level constant rather than importing the private symbol.
- CORS is permissive for local network use (all origins). No auth, no rate limiting — single-user tool.
- No pagination. Callers are responsible for requesting bounded date ranges. Range policy documented in the arch doc.
