# Futures Tick Data Acquisition Architecture

## Overview

Initiative 220 brings tick-level market data into trading-data. It is the project's primary research target: daily bars, minute bars, the TimescaleDB storage tier, the quality operations, and the serving API were all built as the proving ground for the patterns this initiative consumes (initiative plan, entry 220). The data mode is **historical** — purchased tick history, acquired as files and projected into a queryable store — because historical data is what strategies are researched and tested against. Realtime streaming is the end-state of data gathering (process journal, 20260824), but it is a separate initiative with a different process form, and nothing here is built for it beyond not precluding it.

**Scope:** One provider, one venue, one asset class, a deliberately small universe, and the trades tier of market data:

- **Provider:** Databento, and only Databento to start. The provider seam is designed so a second tick provider is an addition, not a redesign, but no second provider is planned in this initiative.
- **Venue and instruments:** CME Globex futures (Databento dataset `GLBX.MDP3`). E-mini S&P 500 (`ES`) first; Gold (`GC`) next; a few more later. The data is priced by volume, so the initial purchase is a bounded range of ES, chosen to prove the pipeline rather than to fill an archive.
- **Schema tier:** trades, and trades with the best bid/offer at the moment of each trade (Databento's `tbbo`). Every top-of-book change (`mbp-1`) and the full order book (`mbo`) are out of scope: they multiply cost, storage, and bandwidth by every quote update rather than every trade, and the data-correctness contract already places order-book depth outside the data layer's guarantees. The tier is a per-instrument configuration so a later slice can add a level without touching the acquisition path.
- **Futures identity:** a futures instrument model — contracts, expirations, active-contract determination, and continuous series under explicit roll methods — which the concept explicitly says does not fit the equities `instruments` registry.
- **Full parity of the operating surface:** the tick tier is a peer of the minute tier everywhere an operator or a client meets the system — CLI command and status surface, `mt data overview`, `mt-run`, the serving API and its two reference documents, and the backup regime. Parity is a delivery of this initiative (PM direction 2026-09-21), not a follow-on.

Out of scope: realtime and intraday capture (its own initiative, streaming form), order-book depth, equity ticks (data-correctness contract: universe too large), cross-venue consolidation, and strategy or replay logic.

**Motivation:** Everything downstream — real-time strategy evaluation, regime detection, replay — needs tick data, and the project has none. The initiative plan's strategy is explicit: prove schema, provider seam, roll logic, storage volume, and query performance against purchased historical data *before* paying for a live subscription. Two things make "prove first" more than caution. The storage tier's own history: minute storage failed on chunk geometry at 7 B rows (journal 20260719, 20260725), and tick carries the same failure modes at one to three orders of magnitude more volume. And the cost model: Databento prices historical data per uncompressed gigabyte by schema, so the schema-tier decision *is* the budget decision, and it must be made from measured sizes, not projections.

## Design Goals

- **Prove the tick tier on purchased data before any subscription** — The first deliverable is a bounded, real ES dataset flowing end to end: purchased, archived, ingested, queried, and cross-checked. Every quantity this initiative depends on — bytes per record per schema, records per session, compressed bytes per row, ingest rate through the chosen write path, query latency at the chosen chunk geometry — is measured on that data, and expansion (more range, GC, more instruments) is a configuration change gated on those measurements.

- **Right-sized capture, not maximal capture** — Trades and trade-with-BBO are the tiers. The choice between them is a measured cost comparison for the same instrument and range, made before purchase. Nothing in the design assumes the finer tiers will ever be wanted; nothing in it prevents adding one.

- **Files are the record; the database is the query tier** — Raw Databento files are retained as the primary historical store (concept, Tick Data). The database holds a projection that can be rebuilt from the files at any time. This is what lets the storage schema evolve — a different chunk interval, a different compression layout, a new derived column — without buying the data again.

- **Futures identity is modelled, not improvised** — Contracts, expirations, provider identifiers, and continuous-series rules are first-class, captured alongside the data from the provider's own definitions. No adjusted or stitched series is ever stored as if it were market data.

- **Full parity with the minute tier, on every surface** — Bounded pass fired by a timer, an `mt-run` kind with its status row and `follow`, `pass_runs` accounting, the `mt data` command and status surface the data-correctness contract requires (I10: status, coverage, update/backfill, daemon-equivalent pass, debug — the contract's `quality` verbs join when 140's quality subgroup exists, which it does not for any granularity today), a row in `mt data overview`, API endpoints with the same freshness posture and reference-documentation coverage as bars, and inclusion in the backup and restore regime. Parity means the minute tier as built: every question an operator or client can ask about minute data today has a tick-tier answer, plus the questions only futures raise (which contract is active under which rule, when it rolls). Parity is delivered in two tiers, in order: *proof parity* — status, coverage, and completeness, which are inputs to the first-purchase go/no-go — lands before the proof; *full parity* — health, accounting, debug reads, product-level `get`, overview lines, the API — lands after it, so the initiative's actual goal, the measured ES dataset, is never held behind a debug verb. Isolation from the equities and Kalshi pipelines holds by design at the schema, migration-track, pass-unit, and credential level: a tick pass failing or a provider outage cannot affect any other source. Host-level isolation — a filling tick volume, memory contention with the minute tier — is a property of the placement decision (Technical Considerations), which this goal constrains rather than assumes; the concurrent-pass contention the 900 plan's arbitration item anticipates is measured on the first purchase and resolved by this initiative (Technical Considerations, "Cross-source arbitration").

## Architectural Principles

- **Acquire and ingest are separate, each idempotent** — Acquisition brings provider data into a local archive as **archive units** and records each in a manifest: what was requested (dataset, schema, symbols, range), how it was delivered (a delivery-mode discriminator — batch job, direct range request, or, later, captured live segment), what the provider returned (job identity where one exists, files, sizes, checksums, record counts), what it cost, and when. For this initiative every unit is a file from a batch job or a persisted direct-range result; the discriminator and the unit abstraction exist from the first migration because they cost nothing at creation and a retrofit for live capture would touch every completeness query. Each unit moves through an explicit state machine recorded in the manifest — *requested → submitted → delivered → downloaded → verified → ingested* (with *failed* reachable from any state, carrying the reason) — and the row is written at *submitted*, the moment money is committed, not after download: a pass that dies between submit and download leaves a submitted unit behind, and the next pass's first phase reconciles in-flight units against the provider's job status before it computes anything new, so the same range is never bought twice and a delivery is never missed inside its retention window (the deadline is a manifest field, and meeting it is enforced, not assumed — Technical Considerations, "Delivery mode and retention"). *Submitted → delivered* is **polled, never waited for**: the provider processes a batch job asynchronously, so the pass polls job status within a bounded wait budget of its own, and a job still running when that budget ends simply rests at *submitted* until the next pass's reconcile phase — resting between passes is a normal state, shown by status as *in flight*, distinct from *pending* (provider has not released the session) and *missing*. Typical job durations and the poll interval are measured on the first purchase, not assumed. Every transition is pass-resumable at unit granularity; a multi-year backfill is many units across many passes, not one long pass. Ingestion reads the archive and projects it into the database, marking the manifest as it goes. Either step can be re-run; re-acquiring an archived range is a no-op, re-ingesting an ingested unit is a no-op, and a database rebuilt from the archive holds row-for-row the same projection (physical layout, including compression state, is not part of the claim).

- **Cost is a first-class input, never a surprise** — No request that costs money is issued without a preceding estimate, and there are no exempt requests: batch jobs, direct range requests, the provider's OHLCV or statistics schemas bought as roll-method inputs or for the validation cross-check — all pass through the same estimate → guard → manifest path, and all deliver into the archive as units. A "probe" that returns billable data outside the archive is a defect. Databento's cost and billable-size queries are free; every acquisition computes the estimate, records it in the manifest, and refuses to proceed past a configured spend ceiling. The provider-side account budget is a second guard, not the first. Bounded initial scope is the PM's decision, made on cost; the pipeline makes the cost visible before each purchase so that decision stays informed.

- **Completeness is answered from the manifest and the raw table** — "What do I have?" for ticks is a join of the manifest (what was purchased and ingested, per instrument and session) with counts from the raw hypertable. It is never answered from a continuous aggregate (journal 20260725, rule 2: a derived object that informs acquisition is a production input, and pausing its refresh silently changes acquisition behaviour). Aggregates over ticks may exist for reads; they never feed the acquisition decision.

- **Chunk geometry is derived from wall-clock span, never from volume** — The archived tick outline's one-hour chunk interval is invalid as written (journal 20260719): over a decade it implies ~87,000 chunks before space partitioning multiplies it, 3.5× the count that made `minute_ohlcv` unusable. The tick hypertable's interval is set explicitly at creation from the table's lifetime ÷ a target chunk count, every aggregate over it sets its own materialization interval explicitly in the same migration (journal 20260725, rule 1), and capacity planning uses measured compressed bytes per row from real data, not compression-ratio projections.

- **Provider records are preserved, not reinterpreted** — Databento's event timestamp, receive timestamp, sequence number, publisher, and instrument identifier are stored as delivered. The natural key is the provider's `(instrument, event time, sequence)`; the project adds nothing to it. Prices arrive as fixed-point integers and stay exact. Tick gaps, if they are ever tracked, are sequence-keyed, not time-window-keyed (concept) — but within a purchased historical range the provider's delivery is complete by contract, so the completeness question is "which sessions were purchased and ingested", not "which sequence numbers are missing".

- **One provider adapter owns the wire format** — Decoding Databento's binary encoding, its symbology, and its delivery modes (batch files and direct range requests) lives in one adapter behind a tick-provider protocol shaped like the existing minute and daily provider protocols. Nothing outside the adapter reads a DBN record. The adapter is the whole surface a second provider would replace. Its execution model is fixed here because it shapes the protocol: the provider's client and decoder are blocking and CPU-bound, so the adapter exposes a synchronous *unit → bounded record batches* iterator that runs off the event loop, feeding the bulk-load path one bounded batch at a time — the bound is the backpressure. Whether that iterator runs in worker threads or worker processes turns on one fact the design cannot supply: whether the provider's Rust-backed decoder releases the interpreter lock while decoding. It is a named slice-design verification item (Technical Considerations, "Ingest throughput"), because a held lock makes threads no faster than the loop and forces a process pool with a different batch-passing model. The pass's asynchronous contract (the shape Kalshi established) orchestrates phases and heartbeats only and never decodes on the loop, so progress stays observable during a multi-gigabyte ingest and the unit's start-timeout budget is spent on work that reports.

- **A futures contract is the instrument; a continuous series is a rule** — Storage is keyed by the actual traded contract. Databento's numeric instrument identifier is dataset-scoped and may be reused across time, so contract definitions are captured with the data and the mapping from identifier to contract is resolved through them, not assumed stable. Continuous series (front-by-calendar, front-by-open-interest, front-by-volume) are roll rules applied at read time to produce a view; they are never a stored series. Calendar spreads and other non-outright instruments under the same product are excluded from the universe unless explicitly configured.

- **The active contract and the roll method are explicit on every surface** — No command, status line, or endpoint that touches a futures product answers without saying which contract it used and which rule chose it. A product-level request (`ES`) resolves to a contract through a named roll method with a project default defined once; a contract-level request (`ESZ6`) bypasses resolution. Status reports the active contract per configured product and rule, its expiration, and the next roll; the API and CLI accept the same method vocabulary. Back-adjustment of prices across rolls is a derived, opt-in read-time transform if it exists at all, never stored, and never the default.

- **Backup is part of done** — The tick archive and the tick database join the backup and restore regime in the same slice cycle that creates them. The archive is the recoverable source, so it is backed up as data; the database projection's backup weight is decided from its rebuild-from-archive cost, measured, and the restore drill covers both. A tick tier that exists only until the next disk failure is not delivered.

- **Sessions, not calendar days** — CME trades nearly around the clock with a daily maintenance break and a Sunday open; a "trading day" spans two calendar dates. Coverage, completeness, and the operator surface are expressed per session. The equities calendar tables are not reused for this; the futures session model is its own — a pure boundary function over a per-product session template plus a stored exception calendar (Technical Considerations, "Session model") — and it is reached through the single session-query function I4 requires, as a second calendar.

- **Pass form for historical, streaming form reserved** — Historical acquisition and ingestion are bounded passes under the production model settled 2026-08-23 (`mt` command → `mt-{source}-pass.service` oneshot + `.timer` under `manta-acquisition.slice`, `mt-run` verb, install-script entry). Historical data becomes available a day behind (Databento publishes a 24-hour embargo on historical access — verify at slice design, since the pass cadence, the pending-versus-missing distinction, and the availability edge all rest on it), so a daily pass is the natural cadence for keeping a configured universe current. A live subscription is the `Type=simple` case and belongs to the realtime initiative; this initiative's obligation to it is concrete and small: the storage schema's natural key and preserved provider fields are delivery-agnostic, the manifest's delivery-mode discriminator and archive-unit abstraction admit a captured segment as a unit, and completeness is defined per unit so a live segment with a disconnect is an incomplete unit, not an undefined state. Sequence-gap tracking is reserved for that initiative; within a purchased historical range the provider's delivery is complete by contract.

- **The third source must not create a third pass shape, and never imports another source** — Two pass frameworks exist today: the EODHD daemon runner and the Kalshi phase/report contract (`PassPhase`, `PhaseReport`, `PassResult`, owned by `data/kalshi/collection_pass.py`). Initiative 120 deferred "daemon framework extraction" to the third source, which is this one. The tick passes follow the Kalshi contract as a *pattern* — the same phase, report, and result shapes, duplicated into the tick package under 120's accept-some-duplication precedent — and import nothing from `data/kalshi`: the dependency direction between two data sources is never source → source, only source → shared foundation. Three copies of one small contract is the evidence that decides whether hoisting it into a shared module is warranted; if it is, that extraction is foundation (9xx) work, not a prerequisite here. A copy drifts: the Kalshi contract has already grown since its first slice (267 added a historical phase), so each 220 slice design diffs the tick copy against the Kalshi original and absorbs what applies — the copy is re-derived per slice, not made once, and the diff is a named task in each slice's task file so it is done and checked off rather than remembered.

- **Operational state has one home; tick data has another** — Run accounting (`pass_runs`) stays where it lives today, in the production TimescaleDB database's minute migration track, for every source including tick: it is the one place `mt data overview`, `mt-run status`, and `/api/v1/overview` read "what ran", and the machinery that closes superseded and abandoned runs (922) operates per database and must not be duplicated. Consequently `PassKind.TICK` lands as a *minute-track* migration that re-renders the `pass_runs` CHECK constraint from the enum (journal 20260901: a served enum grows under you; the applied constraint rejects the new value until a migration re-renders it), never as part of the tick track. The same change gives the new kind its cadence: `schedule_for` in `firing_schedule.py` is a deliberately exhaustive ladder that raises on a kind it does not know, so `PassKind.TICK` lands with its branch there — the one place every kind's firing calendar lives, and what `mt-run status`'s next-firing line and the health check read. The tick database holds tick data and tick-data state only — definitions, manifest, hypertable. Every composing surface (overview, health, accounting, status, the API) therefore reaches the tick database through a second connection pool built from `MT_TICK_DB_URL`. Two failures are kept distinct: the setting *absent* from the environment is a misconfiguration and fails at startup in every process, the way a missing primary URL does today; the tick database *unreachable* is an outage and degrades only the tick surfaces (Technical Considerations, "Serving-layer failure posture"). A silently missing tick line is the failure mode to design out in both cases. The coupling this creates runs in one direction and is accepted: the tick pass opens its run row in the production database before it does anything else and exits non-zero, visible to systemd, if it cannot — a tick pass never runs unaccounted, and a production-database outage degrading tick acquisition is the correct dependency (everything is degraded then), whereas the reverse — tick trouble reaching production — is what the isolation goal forbids.

Nothing tick-shaped runs today. What exists, in order of usefulness:

- **Provider registry (900, complete)** — `ProviderType.DATABENTO` and a Databento `ProviderProfile` (historical base URL, `MT_DATABENTO_API_KEY` as the key variable, aliases) already exist in `providers/types.py` and `providers/profiles.py`. No client, no dependency on the `databento` package, and no key in any environment yet.

## Envisioned State

A configured **tick universe** — instruments (by product and contract selection rule), schema tier per instrument, and the range each is wanted for — drives two bounded passes and one operator surface.

- **Contract definitions** — For each configured product, the provider's instrument definitions for the wanted range are acquired and stored: contract symbol, provider instrument identifier, expiration, tick size, multiplier, and the identifier's validity window. This is the futures instrument model, and it is populated before any tick data, because tick records are keyed by identifiers only the definitions can resolve.

- **Universe resolution** — The configured universe names either explicit contracts or a product with a provider-side continuous symbol (front-by-calendar and so on). Acquisition resolves product → contract *at the provider*, at request time, and the delivered files carry the symbol-mapping records that tie every tick to its real contract. Acquisition therefore never depends on local roll machinery, which is a read-time concern built after data exists; the first purchase needs only definitions and a request. This rests on a premise — that delivered files carry mapping records complete enough to attribute every tick to its contract — which is a named success criterion of the first purchase, not a detail to confirm later. The fallback if it fails is stated now: request by explicit raw contract symbols resolved locally from definitions, which costs the same and removes the dependency on provider-side continuous resolution.

- **Acquisition pass** — Reconciles in-flight units first, then computes the wanted set (universe × range) minus the manifest in the provider's own request grain — calendar-day (UTC) ranges, matching how batch files are split — estimates cost and size for the remainder, refuses above the spend ceiling, and otherwise submits batch requests, polls for delivery within its wait budget, downloads the files into the archive, verifies them, and advances manifest rows. Requests are never session-aligned: a session that spans two calendar days is covered by two units, and which units cover which sessions is a ledger fact established at ingest, not a request-time decision. On a timer, the pass keeps a configured universe current one day behind the market (the embargo figure above, to verify); run manually with a range, it is the backfill. Same command, same state.

- **Ingest pass** — Reads unprocessed archive units, decodes them through the provider adapter, resolves instrument identifiers against definitions, assigns each record its session through the boundary function, and bulk-loads the tick hypertable on the tick database. Resumption is at **unit boundary by design**: a unit's ledger rows and its *ingested* transition commit together, after its last batch, so a pass that dies mid-unit leaves raw rows the next attempt's natural-key conflict-ignore skips and no ledger rows — completeness never sees a half-ingested unit. Re-decoding a partially ingested unit is the accepted cost of that simplicity; the first purchase measures whether intra-unit checkpoints are *needed*, not whether they are supported.

- **Storage** — A `tick` migration track on the tick database instance. One hypertable for the trades tier — trade fields always present, best-bid/offer fields present when the instrument's tier includes them — with chunk interval set from wall-clock span and any read-side aggregates created per the journal rules. The tier (`trades` or `tbbo`, the provider's own schema names) is a property of the instrument's configuration and is recorded on each archive unit and ledger row; it is never a column on the tick row, because under this model a quote is not an event of its own but an attribute of a trade, and a row whose BBO fields are null is a trades-tier row by construction. Slice 105's `TickEventType` enum (`trade`/`quote`) and its unit test belong to the discriminator model this replaces; the tick storage track removes them along with 105's stale integration test, and the tier vocabulary is a new enum in the tick package. Because the table is created before the proof measures it, the initial interval is deliberately conservative — on the order of the minute tier's proven geometry, derived from the same rule — so the proof validates rather than invalidates the schema; if it invalidates anyway, the accepted remedy is a rebuild from the archive, which the file-first principle makes a compute cost rather than a repurchase. The definitions, manifest, and ingest-ledger tables live alongside it. Physical grouping by instrument — space partitioning *and* the compression layout (the candidate is segment by instrument, order by event time and sequence) — is one class of decision and is made once, from the first purchase's measurements, not inherited from the 105 outline: per-instrument row counts for a liquid front contract and a thin deferred one differ by orders of magnitude, which is where a single global choice hurts.

- **Operator surface, at minute parity** — Every verb the minute tier answers has a tick-tier answer: status (per product and contract: sessions complete, pending, failed; the active contract per roll rule and the next roll), coverage per session, `pull`/backfill and ingest, `get` for ticks and for bars derived from ticks (by contract or by product-plus-roll-method), health and accounting lines, and debug reads of manifest and definitions. Whether this is an `mt data tick` subgroup (the Kalshi shape) or `--granularity tick` on the existing commands (the minute shape) is a slice-design decision; the constraint is that the same questions are answerable with the same defaults. `mt-run tick` and `mt-run follow tick`, a `tick` row in `mt-run status`, `PassKind.TICK` in `pass_runs`, and a tick line in `mt data overview` — reachable in production as `mt-run data overview` — complete the picture. Process status from systemd, data status from persisted state — the two layers the 2026-08-23 ADR requires.

- **Serving surface, at bars parity** — The API serves ticks and tick-derived bars for a contract or for a product under a named roll method, the contract catalog (definitions, expirations, the active contract per rule), and tick freshness and coverage in `/api/v1/status` and `/api/v1/overview`. Both reference documents (`docs/api/reference.md`, `docs/api/agents.md`) cover the new endpoints under the 190 documentation gate, and `openapi.json` is regenerated at each slice close.

- **Backup and restore** — The archive directory and the tick database are enrolled in the 915/920 regime: the archive in the backup set as data, the database with a policy chosen from measured rebuild cost, both exercised by the restore drill. Retention, exclusions, and host placement are recorded in the backup runbook, not only here.

- **Validation loop** — Minute bars derived from ingested ticks are compared with the provider's own inexpensive OHLCV schema for the same instrument and sessions. Agreement proves the decode, the identifier resolution, the session boundaries, and the storage projection together; disagreement localizes the defect. This is the initiative's correctness check, cheap enough to run on every ingest. Its two inputs arrive as separate archive units — the tick unit and the OHLCV unit for the same range — so the acquisition pass requests them together (the OHLCV companion is part of the wanted set, and of the estimate, for any tick range), and the ingest pass runs the comparison for every instrument-session whose inputs are *both* ingested, recording the outcome on the ledger row: *verified*, *mismatch*, or *unverified* with the missing input named. An unverified session is re-checked on every later ingest pass until it resolves and is counted as unverified by status — never silently skipped. "Runs on every ingest" means every ingest advances every session it can.

**Completeness definitions** (the analogue of 120's caught-up and 260's complete-market definitions), stated at the grain the manifest actually has. Provider files are split by calendar day and hold many instruments, so a unit's record count says nothing about one instrument-session; the join is made once, at ingest, when the decoder sees every record anyway: ingestion writes an **ingest ledger** row per *(instrument, session)* — records loaded, first and last event time, source unit — and status reads that ledger, never re-decoding. An *archive unit is complete* when its state is *ingested*. An *instrument-session is complete* when every unit covering it is complete and the raw table's count for that instrument-session equals the ledger's. The *universe is caught up* when every configured instrument is complete for every session in its wanted range up to the **availability edge**, which is not a local rule: each pass records the provider's free dataset metadata — the dataset's available range and its per-day condition (available, pending, degraded, missing) — and a session the provider reports as pending is *pending*, one it reports as missing or degraded is surfaced as such, and one the metadata cannot be fetched for is *edge unknown*. The 24-hour embargo is the expected lag behind that edge, used for the timer cadence and for flagging an edge that stops advancing; it is never used to infer that a session is missing.

At completion, a small ES (then GC) tick history sits in the archive and the database, every number the realtime initiative and the tick-serving work need has been measured on it, and expanding the universe is a configuration edit followed by a cost estimate — one that includes any roll-method inputs the added range needs, since figures derived from ticks exist only for sessions already bought.

## Technical Considerations

- **Schema tier is the cost decision** — The three candidate tiers differ by what triggers a record: a trade (`trades`), a trade plus the book state just before it (`tbbo` — same record count as trades, wider records), or every top-of-book change (`mbp-1` — many times the record count for a liquid contract). Slice design must obtain billable size for each tier over the *same* ES range from the provider's free estimation endpoints before the first purchase, and record the numbers; the tier choice, and whether GC follows at the same tier, are made from those figures. Record sizes and per-session volumes are to be verified from Databento's schema documentation and measured, not assumed.

- **Delivery mode and retention** — Databento serves history two ways that yield identical data: a direct range request streamed into the client, and an asynchronous batch job that produces files (split by day by default, zstd-compressed) retained for a limited window and downloadable within it. The file-first principle points at batch for anything that will be archived; direct requests suit small probes and estimates. The retention window and any size limits per mode must be verified during slice design, since a download that misses the window is a repurchase. The window is a deadline, and "the next pass runs before it" is not a guarantee — a disabled timer or a host outage breaks it — so four things make it one. *Ordering*: the reconcile phase downloads every deliverable unit, earliest deadline first, before it estimates or submits anything new; downloads are free and submissions cost money, so that order is always right. *Explicit expiry*: a unit whose deadline passes undelivered transitions to *failed* with reason *retention expired* and re-enters the wanted set; its repurchase is a new unit whose manifest row names the expired one, so the repeat cost appears in the estimate and the accounting rather than vanishing into a retry. *Escalation*: the health check (919) reports any in-flight unit whose deadline falls before the tick pass's next scheduled firing (`schedule_for`, the same source `mt-run status` reads) as a finding that needs a human, and the operator runs the pass by hand. *Cadence bounded by the window*: slice design verifies the provider's window and requires it to cover several consecutive missed firings; if it does not, the pass fires more often — the window is the provider's fact, the cadence is ours.

- **Availability lag and licensing** — Historical access is embargoed at 24 hours (as published on Databento's roadmap at architecture time; verify at slice design) and requires no license; intraday and realtime require a live plan (CME live moved from usage-based to subscription plans in April 2025; the entry plan was announced at $179/month and the pricing page currently lists Standard at $199/month — verify at the time of any decision) plus CME's pass-through license fee, which depends on the subscriber's status. None of that is needed for this initiative; it fixes the historical pass cadence at daily, one session behind, and is the reason realtime is separate. Historical purchases are usage-based per uncompressed gigabyte with no subscription; new accounts carry a small expiring credit that can fund the first measurement.

- **Futures identity and symbology** — Databento resolves symbols four ways: raw contract symbols, dataset-scoped numeric instrument identifiers, parent symbols covering a whole product (including spreads), and continuous symbols (`.c`, `.n`, `.v` — calendar, open-interest, and volume roll rules — with a depth index). Continuous symbols are a *request* convenience that maps to real contracts over time; the data carries the real contract's identifier. The instrument model must therefore store definitions and their validity windows, treat identifier reuse as expected, and derive continuous views from stored rules. Exact roll semantics and the mapping-message behaviour in delivered files are slice-design verification items.

- **Session model** — CME's trading day, maintenance break, Sunday open, and holiday schedule define the session boundaries that coverage, completeness, the ingest ledger, and the derived-bar cross-check all depend on; the equities calendar in the storage layer does not describe them, and the model is load-bearing enough that its shape is fixed here rather than at slice design. It has two parts. A **pure boundary function** — given a product and an event timestamp, return the session identifier and its bounds — driven by a per-product *session template* (weekly open, daily close, maintenance break, all in exchange time), which is code and configuration, not data. And a **stored exception calendar** — holidays, early closes, and any exchange-declared irregular session — seeded from CME's published trading-hours schedule, which is public and free, and cross-checked against the provider's exchange-status records only if those are ever purchased; no purchase is required to build it. The function is served through the single session-query surface I4 mandates, as a second calendar, so hard-coded CME hours anywhere else remain the defect I4 names. The design carries its own proof: if the boundaries are wrong, daily bars derived from ingested ticks disagree with the provider's daily OHLCV for the same contract, so the first purchase's cross-check validates the session model along with everything else. The template values and the calendar's seed are slice-design verification items; the interface is not.

- **Database placement and roles** — `MT_TICK_DB_URL` exists but points nowhere. A separate instance can mean a second database on the production cluster, a second cluster on the production host, or a second host; each has a different answer for memory contention with the minute tier, for backup (915) and least-privilege roles (913), and for the test cluster (917). Two constraints apply to all three. First, composition is cross-database under every option — PostgreSQL does not join across databases — so overview, health, accounting, status, and the API server (built today around one URL, `create_app(db_url=…)`, 187 D9) each gain a second pool from `MT_TICK_DB_URL`, and that variable must be present in every service environment file the passes and `mt-serve` run under; the tick pass writes its run row to the production database over its own second connection. The migration CLI is single-database today (`migrate apply` resolves one maintenance URL, and its own comment records that every track targets the same database), so a tick track on another instance needs track → URL routing, a second migration ledger, a second maintenance credential with its own grant artifact under 913's separation, and a cold-start path (`mt data init`) that knows two databases. That touches every migration and credential code path, which is foundation work, not tick work: it is slice 923 of the foundation-cleanup plan, sequenced before the tick storage track (Anticipated Slices). Second, the parity goal's isolation claim disqualifies any placement in which a filling tick volume or a runaway tick query can take down production storage — a shared cluster or host needs a separate volume and a resource bound, or it is not a candidate. The decision is the PM's, informed by the first purchase's measured size; the architecture requires that the tick track never shares a hypertable, chunk geometry, or refresh policy with the minute tier.

- **Cross-source arbitration** — 916 supervises each source independently and installs `manta-acquisition.slice` with no resource settings, because the numbers were speculative until there was measured contention; 260 inherited the gap and named this initiative's tick volume as what makes it real; the 900 plan's Future Work records that the solution belongs to the initiative that brings the new sources, not to maintenance. It belongs here, then, and it is answered in two steps that follow the prove-first structure. Before the proof, the mitigation is the one 916 already uses: the tick pass's firing calendar is chosen to stagger against the minute pass's known firing times, and bounded ingest batches make the tick write load steady rather than bursty. The first purchase then measures the contention itself — the tick ingest pass running concurrently with the minute pass, recording the minute pass's duration and the host's I/O, memory, and database write throughput against its solo baseline. The steady-state slice sets `IOWeight`/`CPUWeight`/`MemoryMax` on the slice from those numbers and chooses among the three mechanisms the 900 plan lists — a resource-class lock the passes take, a scheduler inside `mt`, or calendar stagger kept as-is — on that evidence. Setting weights before the measurement would repeat the mistake 916 declined to make.

- **Ingest throughput and the write path** — Bulk load through `COPY` into a hypertable is the candidate path; its rate on tick rows is re-measured on the first purchase, never recalled from the minute tier's figures (journal 20260720: recorded numbers are re-measured, not recalled). Tick sessions are far larger than minute days; decode cost (the provider's Rust-backed decoder versus per-record Python), whether that decoder releases the interpreter lock (which decides threads versus processes for the adapter's execution model), batch sizing, and whether unit-boundary resumption's re-decode cost justifies intra-unit checkpoints are measured there too. The measurement has a pass/fail: a day's sessions for the configured universe must ingest well inside the daily pass interval, or the cadence the embargo argument selects does not hold.

- **Active contract and roll methods** — Calendar (expiration-based, possibly with a configured offset of days before expiry), open-interest, and volume rules each need different inputs: calendar needs only definitions; open-interest and volume need per-contract daily figures, which come either from the provider's statistics or OHLCV schemas (cheap, but a purchase) or from counts derived over ingested ticks (free, but only for sessions already bought). The rule vocabulary must match the provider's continuous-symbol conventions closely enough that a request phrased in either resolves to the same contract on the same day, and the resolution must be reproducible: a status line or API response that names the active contract can be re-derived later from stored definitions and stored figures — which means purchased figures are archive units with manifest provenance like any other purchase, and derived figures are recomputable from the raw table. Because derived figures exist only for sessions already bought, expanding a universe backward carries the cost of roll inputs for the old range, and the estimate says so. Roll-day handling (the session on which the rule switches, and whether both contracts' ticks are served across it) is a slice-design decision with a stated default.

- **Own subgroup or granularity switches** — The minute tier is reached through `--granularity` on shared commands (`status`, `pull`, `daemon`, `get`); Kalshi has its own `mt data kalshi` subgroup because its identity model differs. Futures identity differs too (contract, product, roll method), which argues for a subgroup, while I10's "same shape" rule argues for switches. Whichever is chosen, `mt data overview`, `health`, and `accounting` gain tick lines in place, and the API mirrors the same choice — a `/api/v1/futures/*` namespace after 188's Kalshi precedent, or tick as a granularity on `/api/v1/bars/{symbol}` with contract and roll-method parameters. The two surfaces make one decision, not two.

- **Backup coverage** — The archive is the recoverable source of truth and is backed up as data. The database projection's policy — full base-backup weight, WAL-only, or rebuild-from-archive on restore — is chosen from the measured rebuild cost of the first purchase, and the restore drill proves whichever is chosen. If the tick database lands on a second host or cluster, the 915/920 tooling (base backups, WAL archiving, keep-days, exclusions) is extended to it rather than duplicated by hand; the same applies to the 913 role set.

- **Serving-layer failure posture** — The API's lifespan opens its pools eagerly and fails at startup if the primary database is unreachable (187 D9's `create_app(db_url=…)` exists so the load tier never reads the production URL from the environment). Copying that posture for the tick pool would let a tick-instance outage stop `mt-serve` from starting — the parity goal defeating the isolation goal. The decision: `mt-serve` starts without the tick database; the tick pool is opened at startup but its failure is recorded, not raised; tick endpoints answer `503` with the API's existing error shape while the pool is down and recover when it returns; `/api/v1/health` reports the tick pool alongside the primary; equities routes never consult it. This is a new posture for the codebase, chosen deliberately for one class of surface, and `create_app` gains a `tick_db_url` seam so the load tier's discipline covers tick endpoints too. The same split applies to `mt data overview` and `health`: a tick line that reads "unreachable" is the correct output, not an omitted line.

- **Data-correctness contract amendment** — The contract is normative and says this initiative inherits I2–I10 and adds tick-specific invariants "when initiative 200 lands"; adding them is a deliverable here, not an afterthought. Three points are settled now. **I4** (exactly one trading-session function in the codebase): the futures session model is a second *calendar* served through the same single session-query surface, never a second function — hard-coded CME hours anywhere are the defect I4 names. **I7** (independent cross-vendor audit): unsatisfiable for tick by this initiative's scope — one provider, no cross-venue consolidation — and the derived-bar check against the provider's own OHLCV is *verification* in the contract's vocabulary, not audit; the amendment records the exception rather than letting the contract claim what the scope cannot deliver. **Vocabulary**: tick completeness is manifest-based, not `acquisition_state`-based, and `granularity = 'tick'` enters the minute track's enumerations (`data_gaps`, `data_status`) only where a surface actually reads them; the amendment lists which.

- **Relationship to 240 (flat-file import)** — 240 is a generic import tool for CSV/Parquet/provider exports into the existing acquisition-state universe. 220's archive → manifest → ingest shape is the more general pattern; 240 should instantiate it for other formats rather than 220 borrowing from a tool that does not yet exist. DBN decoding stays inside 220's provider adapter.

- **Relationship to the serving API (180)** — 180's exclusions deferred tick endpoints until tick storage exists; this initiative supplies both the storage and the endpoints, closing that exclusion. 180's standing design question — "does this belong in the API?" — is answered per endpoint at slice design, with the futures session model and roll methods as inputs, and 190's documentation gate is the acceptance check.

- **Testing strategy** — Per project rules: unit tests over real provider files (small purchased or sample DBN files as fixtures — a fixture in an invented format is a false pass), integration tests against a throwaway tick database per the dedicated test cluster, and passes testable as functions of (manifest, provider results) → (new manifest, writes). The estimate-before-purchase guard is tested with a mocked cost response, never against the live account.

- **Secrets and spend guards** — The API key enters through `MT_DATABENTO_API_KEY` only; it is not yet present in any environment. A provider-side account budget is configured before the first request as the second guard behind the local spend ceiling.
