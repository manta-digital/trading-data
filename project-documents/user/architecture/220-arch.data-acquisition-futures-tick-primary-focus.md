# Futures Tick Data Acquisition Architecture

## Overview

Initiative 220 brings tick-level market data into trading-data. It is the project's primary research target: daily bars, minute bars, the TimescaleDB storage tier, the quality operations, and the serving API were all built as the proving ground for the patterns this initiative consumes (initiative plan, entry 220). The data mode is **historical** — tick history acquired as files and projected into a queryable store — because historical data is what strategies are researched and tested against. The data arrives in three stages (PM direction 2026-09-27; Technical Considerations, "Sourcing sequence and plan"): first the ES batch files already bought with Databento's free credits and verified locally; then the history included in Databento's Standard plan once it is subscribed; and only rarely a purchase outside the plan. Realtime streaming is the end-state of data gathering (process journal, 20260824), but it is a separate initiative with a different process form, and nothing here is built for it beyond not precluding it.

**Scope:** One provider, one venue, one asset class, a deliberately small universe, and the trades tier of market data:

- **Provider:** Databento, and only Databento to start. The acquisition side of the provider seam — the adapter protocol, the manifest, the pass shape — is designed so a second tick provider is an addition. The storage projection is not provider-neutral and does not pretend to be: its natural key, preserved columns, and tier vocabulary are Databento's (Architectural Principles, "Provider records are preserved"). A second provider whose records differ in shape means a new projection and a rebuild from the archive, which the file-first principle makes a compute cost rather than a redesign. No second provider is planned in this initiative.
- **Venue and instruments:** CME Globex futures (Databento dataset `GLBX.MDP3`). E-mini S&P 500 (`ES`) first; Gold (`GC`) next; a few more later. The data is priced by volume, so the initial purchase is a bounded range of ES, chosen to prove the pipeline rather than to fill an archive.
- **Schema tier:** trades, and trades with the best bid/offer at the moment of each trade (Databento's `tbbo`). Every top-of-book change (`mbp-1`) and the full order book (`mbo`) are out of scope: they multiply cost, storage, and bandwidth by every quote update rather than every trade, and the data-correctness contract already places order-book depth outside the data layer's guarantees. The tier is a per-instrument configuration so a later slice can add a level without touching the acquisition path.
- **Futures identity:** a futures instrument model — contracts, expirations, active-contract determination, and continuous series under explicit roll methods — which the concept explicitly says does not fit the equities `instruments` registry.
- **Full parity of the operating surface:** the tick tier is a peer of the minute tier everywhere an operator or a client meets the system — CLI command and status surface, `mt data overview`, `mt-run`, the serving API and its two reference documents, and the backup regime. Parity is a delivery of this initiative (PM direction 2026-09-21), not a follow-on.

Out of scope: realtime and intraday capture (its own initiative, streaming form), order-book depth, equity ticks (data-correctness contract: universe too large), cross-venue consolidation, and strategy or replay logic.

**Motivation:** Everything downstream — real-time strategy evaluation, regime detection, replay — needs tick data, and the project has none. The initiative plan's strategy is explicit: prove schema, provider seam, roll logic, storage volume, and query performance against purchased historical data *before* paying for a live subscription. Two things make "prove first" more than caution. The storage tier's own history: minute storage failed on chunk geometry at 7 B rows (journal 20260719, 20260725), and tick carries the same failure modes at one to three orders of magnitude more volume. And the cost model: Databento prices historical data per uncompressed gigabyte by schema, so the schema-tier decision *is* the budget decision, and it must be made from measured sizes, not projections.

## Design Goals

- **Prove the tick tier on data already in hand before any subscription** — The first deliverable is a bounded, real ES dataset flowing end to end: archived, ingested, queried, and verified. The two ES batch jobs already bought with the free credits (27.7 M records: `trades` 2024-08-30 → 09-29 and `tbbo` 2024-11-01 → 12-31, each verified against its `manifest.json` SHA-256 and the job's `record_count`) are that dataset. Both ranges contain a quarterly ES roll. Every quantity this initiative depends on — bytes per record per schema, records per session, compressed bytes per row, ingest rate through the chosen write path, query latency at the chosen chunk geometry — is measured on that data, and expansion (more range, GC, more instruments) is a configuration change gated on those measurements.

- **Right-sized capture, not maximal capture** — Trades and trade-with-BBO are the tiers. The choice between them is a measured cost comparison for the same instrument and range, made before purchase. Nothing in the design assumes the finer tiers will ever be wanted; nothing in it prevents adding one.

- **Files are the record; the database is the query tier** — Raw Databento files are retained as the primary historical store (concept, Tick Data). The database holds a projection that can be rebuilt from the files at any time. This is what lets the storage schema evolve — a different chunk interval, a different compression layout, a new derived column — without buying the data again.

- **Futures identity is modelled, not improvised** — Contracts, expirations, provider identifiers, and continuous-series rules are first-class, captured alongside the data from the provider's own definitions. No adjusted or stitched series is ever stored as if it were market data.

- **Full parity with the minute tier, on every surface** — Bounded passes run by hand, with the production form — timer, `mt-run` kind with its status row and `follow`, and `pass_runs` accounting — arriving with the cadence decision, which is deferred (Technical Considerations, "Cadence"), the `mt data` command and status surface the data-correctness contract requires (I10: status, coverage, update/backfill, daemon-equivalent pass, debug — the contract's `quality` verbs join when 140's quality subgroup exists, which it does not for any granularity today), a row in `mt data overview`, API endpoints with the same freshness posture and reference-documentation coverage as bars, and inclusion in the backup and restore regime. Parity means the minute tier as built: every question an operator or client can ask about minute data today has a tick-tier answer, plus the questions only futures raise (which contract is active under which rule, when it rolls). Parity is delivered in two tiers, in order: *proof parity* — status, coverage, and completeness, which are inputs to the first-purchase go/no-go — lands before the proof; *full parity* — health, accounting, debug reads, product-level `get`, overview lines, the API — lands after it, so the initiative's actual goal, the measured ES dataset, is never held behind a debug verb. Isolation from the equities and Kalshi pipelines holds by design at the schema, migration-track, pass-unit, and credential level: a tick pass failing or a provider outage cannot affect any other source. Two things are shared on purpose and are the only exceptions to the migration-track axis, each landing as a minute-track migration in the production database: run accounting (`PassKind.TICK` in `pass_runs` — Architectural Principles, "Operational state has one home") and the CME calendar in the shared calendar tables (Technical Considerations, "Session model"). Both are operational and reference state that other surfaces already read from one home, and neither holds tick data. Host-level isolation — a filling tick volume, memory contention with the minute tier — is a property of the placement decision (Technical Considerations), which this goal constrains rather than assumes; the concurrent-pass contention the 900 plan's arbitration item anticipates is measured by the proof and resolved by this initiative (Technical Considerations, "Cross-source arbitration").

## Architectural Principles

- **Acquire and ingest are separate, each idempotent** — Acquisition brings provider data into a local archive as **archive units** and records each in a manifest: what was requested (dataset, schema, symbols, range), how it was delivered (a delivery-mode discriminator — batch job, direct range request, or, later, captured live segment), what the provider returned (job identity where one exists, files, sizes, checksums, record counts), what it cost, and when. For this initiative every unit is a file from a batch job or a persisted direct-range result; the discriminator and the unit abstraction exist from the first migration because they cost nothing at creation and a retrofit for live capture would touch every completeness query. Each unit moves through an explicit state machine recorded in the manifest — *requested → submitted → delivered → downloaded → verified → ingested* (with *failed* reachable from any state, carrying the reason). The row is written at *requested*, immediately before the submit and carrying the estimate, so a submit whose outcome is unknown leaves a row to reconcile against the account's job list instead of no trace. A successful submit moves it to *submitted*, the moment money is committed, not after download. Adopted files enter at *downloaded*: a pass that dies between submit and download leaves a submitted unit behind, and the next pass's first phase reconciles in-flight units against the provider's job status before it computes anything new, so the same range is never bought twice and a delivery is never missed inside its retention window (the deadline is a manifest field, and meeting it is enforced, not assumed — Technical Considerations, "Delivery mode and retention"). *Submitted → delivered* is **polled, never waited for**: the provider processes a batch job asynchronously, so the pass polls job status within a bounded wait budget of its own, and a job still running when that budget ends simply rests at *submitted* until the next pass's reconcile phase — resting between passes is a normal state, shown by status as *in flight*, distinct from *pending* (provider has not released the session) and *missing*. Typical job durations and the poll interval are measured on the first batch job the pass submits, not assumed. Every transition is pass-resumable at unit granularity; a multi-year backfill is many units across many passes, not one long pass. Ingestion reads the archive and projects it into the database, marking the manifest as it goes. Either step can be re-run; re-acquiring an archived range is a no-op, re-ingesting an ingested unit is a no-op, and a database rebuilt from the archive holds row-for-row the same projection (physical layout, including compression state, is not part of the claim). Each unit also carries the minute tier's fetch-state vocabulary, `FetchStatus` (PM direction 2026-09-27): an attempt count; `FAILED_RETRYABLE` after a failed attempt, until a configured attempt limit makes it `RETRY_EXHAUSTED`; and `PROVIDER_HOLE` when the provider reports every day of the unit as missing, or delivers nothing where the calendar says trading occurred. Status reports each of these, and a manual reset reopens exhausted units, as minute's gap reset does. `PROVIDER_HOLE` follows the minute meaning: terminal, not "still asking", and a holed session is excluded from *caught up*, as it is in minute, while status shows it as a hole. The one difference: the provider can later fill a day it once reported missing. A holed unit therefore reopens automatically when the day-condition metadata for its days changes (a newer `last_modified_date`, or a better condition), and a manual reset reopens it too. None of it needs a schedule.

- **Cost is a first-class input, never a surprise** — No request that costs money is issued without a preceding estimate, and there are no exempt requests: batch jobs, direct range requests, and the provider's statistics schema if it is ever bought as a roll-method input — all pass through the same estimate → guard → manifest path, and all deliver into the archive as units. A "probe" that returns billable data outside the archive is a defect. Databento's cost and billable-size queries are free; every acquisition computes the estimate, records it in the manifest, and refuses to proceed past a configured spend ceiling. There are two local ceilings. `MT_TICK_SPEND_CEILING_USD` is the most one acquisition pass may commit, summed over the units it would submit. A **rolling 30-day cap**, `MT_TICK_SPEND_30D_CEILING_USD` (PM direction 2026-09-27), is the most the manifest may show committed over the trailing 30 days, including the pass's own units. It is summed from the manifest, which records each unit's estimate at *requested* and the provider's actual cost once the job reports it. The sum uses the actual where known and the estimate otherwise, so an overrun counts as soon as the provider reports it. That is the cap working, not a stall: while the trailing sum is at or over the cap, passes refuse to buy and say by how much and until when. Downloads, ingest, and status go on. The PM raises the cap or waits it out. A provider job state the adapter does not recognize moves the unit to *failed* with the state named, rather than leaving it submitted forever. Today the adapter refuses such a job record loudly; the pass maps that refusal to the unit. It needs no state of its own. Both settings are checked before any submit and neither has a default. If either is absent, the pass still estimates and reports but refuses to purchase. A manual backfill that needs more raises the per-pass ceiling for that run rather than bypassing it. The provider-side account access limit (set by the PM 2026-09-27) is the outer guard, not the first. Under the Standard plan, requests for included data may price at $0; the guard compares whatever `get_cost` reports, so a $0 unit passes and an out-of-plan unit is priced as before. Whether `get_cost` does report $0 for plan-included data is verified when the plan is subscribed. Bounded initial scope is the PM's decision, made on cost; the pipeline makes the cost visible before each purchase so that decision stays informed.

- **Completeness is answered from the manifest and the raw table** — "What do I have?" for ticks is a join of the manifest (what was purchased and ingested, per instrument and session) with counts from the raw hypertable. It is never answered from a continuous aggregate (journal 20260725, rule 2: a derived object that informs acquisition is a production input, and pausing its refresh silently changes acquisition behaviour). Aggregates over ticks may exist for reads; they never feed the acquisition decision.

- **Chunk geometry is derived from wall-clock span, never from volume** — The archived tick outline's one-hour chunk interval is invalid as written (journal 20260719): over a decade it implies ~87,000 chunks before space partitioning multiplies it, 3.5× the count that made `minute_ohlcv` unusable. The tick hypertable's interval is set explicitly at creation from the table's lifetime ÷ a target chunk count, every aggregate over it sets its own materialization interval explicitly in the same migration (journal 20260725, rule 1), and capacity planning uses measured compressed bytes per row from real data, not compression-ratio projections.

- **Provider records are preserved, not reinterpreted** — Databento's event timestamp, receive timestamp, sequence number, publisher, and instrument identifier are stored as delivered. The natural key is the provider's `(instrument, event time, sequence)`; the project adds nothing to it. Prices arrive as fixed-point integers and stay exact. Tick gaps, if they are ever tracked, are sequence-keyed, not time-window-keyed (concept) — but within a purchased historical range the provider's delivery is complete by contract, so the completeness question is "which sessions were purchased and ingested", not "which sequence numbers are missing".

- **Every row knows its unit; replacing data is a supersession, never a silent conflict** — Each tick row carries its archive unit's integer identifier: not a string, and not part of the natural key. Delivery mode and provenance are reached through the manifest (PM direction 2026-09-27). Re-ingesting a unit is idempotent: its own rows conflict-ignore. Natural-key conflict-ignore never decides between two *different* units. When one unit replaces others, the superseded units' rows are deleted and the new unit's loaded in one transaction, and the manifest records which unit superseded which. In this initiative every unit is a calendar-day unit, so supersession is always whole-day over whole-day. The ranges nest exactly, and each transaction spans one day's delete and load, not a multi-gigabyte history. Superseding a sub-day live segment (a partial range) is the realtime initiative's to define. The per-row unit id is what makes that possible (delete by unit and time range), and the ledger would need a per-unit time range for it. Neither is built here. That covers historical data over live capture (the default precedence, PM direction 2026-09-27; the slice that builds live capture states any exceptions), a tier upgrade over loaded history (`tbbo` over `trades` shares the natural key and would otherwise silently no-op), and a provider correction. The ingest ledger's per-unit grain is what makes the replacement exact.

- **One provider adapter owns the wire format** — Decoding Databento's binary encoding, its symbology, and its delivery modes (batch files and direct range requests) lives in one adapter behind a tick-provider protocol shaped like the existing minute and daily provider protocols. Nothing outside the adapter reads a DBN record. The adapter is the whole acquisition-side surface a second provider would replace. Its execution model is fixed here because it shapes the protocol: the provider's client and decoder are blocking and CPU-bound, so the adapter exposes a synchronous *unit → bounded record batches* iterator that runs off the event loop, feeding the bulk-load path one bounded batch at a time — the bound is the backpressure. The bound is a byte budget, one named constant (`TICK_DECODE_BATCH_BYTES`). Each file's record count per batch is derived from it by the file's record size, so the bound holds across 48-byte trades and 520-byte definitions (220 slice design). The proof re-sets it from measurements; until then it is conservative. Because the worker that decodes a batch also writes it (below), batches never cross a process boundary under either execution model — only progress does — so the threads-versus-processes answer changes where the worker runs, not how batches move. Slice 220 answered the threads-versus-processes question. The SDK's per-record decoder holds the interpreter lock, but the array-batch path the iterator uses releases it during decompression. A benchmark on real records showed 3.2–3.7× at 4 threads for the array path and no gain for the per-record path, so workers are threads. The proof re-checks this on real volume. The write side follows the same rule. `COPY` through the project's synchronous psycopg connections blocks the thread that issues it. So the worker that decodes a unit also writes it, over a dedicated connection it owns for that unit, issuing each bounded batch's `COPY` and returning only progress to the loop. This is a deliberate break from the Kalshi shape of one locked connection used from async phases. That shape suits Kalshi's small writes, not multi-gigabyte loads. It also keeps a unit's ledger rows and its *ingested* transition on the connection that loaded its rows. The pass's asynchronous contract (the shape Kalshi established) orchestrates phases and heartbeats only and never decodes or bulk-writes on the loop, so progress stays observable during a multi-gigabyte ingest and the unit's start-timeout budget is spent on work that reports.

- **A futures contract is the instrument; a continuous series is a rule** — Storage is keyed by the actual traded contract. Databento's numeric instrument identifier is dataset-scoped and may be reused across time, so contract definitions are captured with the data and the mapping from identifier to contract is resolved through them, not assumed stable. Continuous series (front-by-calendar, front-by-open-interest, front-by-volume) are roll rules applied at read time to produce a view; they are never a stored series. Calendar spreads and other non-outright instruments under the same product are excluded from the universe unless explicitly configured.

- **The active contract and the roll method are explicit on every surface** — No command, status line, or endpoint that touches a futures product answers without saying which contract it used and which rule chose it. A product-level request (`ES`) resolves to a contract through a named roll method with a project default defined once; a contract-level request (`ESZ6`) bypasses resolution. Status reports the active contract per configured product and rule, its expiration, and the next roll; the API and CLI accept the same method vocabulary. Back-adjustment of prices across rolls is a derived, opt-in read-time transform if it exists at all, never stored, and never the default.

- **Backup is part of done** — The tick archive joins the backup regime in the slice that first writes it: 223, which adopts the free-credit files. The archive is the record, and losing it means a repurchase, or for data no longer sold, a permanent loss. The database projection can be rebuilt from the archive, so its policy is chosen once the proof has measured the rebuild cost (227). Until then, the exposure is a rebuild from a backed-up archive, not lost data. The archive is the recoverable source, so it is backed up as data; the database projection's backup weight is decided from its rebuild-from-archive cost, measured, and the restore drill covers both. A tick tier that exists only until the next disk failure is not delivered.

- **Sessions, not calendar days** — CME trades nearly around the clock with a daily maintenance break and a Sunday open; a "trading day" spans two calendar dates. Coverage, completeness, and the operator surface are expressed per session. The equities *calendar* is not reused for this; the futures session model is its own — a CME calendar of trading-hours schedule, session rows, and exceptions (Technical Considerations, "Session model") — and it is reached through the single session-query function I4 requires, as a second calendar in the calendar tables that function already reads.

- **Pass form for historical, streaming form reserved** — Historical acquisition and ingestion are bounded passes under the production model settled 2026-08-23 (`mt` command → `mt-{source}-pass.service` oneshot + `.timer` under `manta-acquisition.slice`, `mt-run` verb, install-script entry). Historical data becomes available about **8 hours** behind the market (measured 2026-09-27: the dataset's available end sat exactly 8 hours before the time of each query, and every day up to the current one reported `available`; the architecture's earlier 24-hour figure is superseded). **No daily history pull is assumed** (PM direction 2026-09-27): history is pulled on demand — for development and testing, to take the plan's included year, and to catch up after the realtime feed lags or drops. The steady state is realtime, which belongs to its own initiative. Whether the acquisition pass gets a timer at all, and at what cadence, is an open PM decision (Technical Considerations, "Cadence"). A live subscription is the `Type=simple` case and belongs to the realtime initiative; this initiative's obligation to it is concrete and small: the storage schema's natural key and preserved provider fields are delivery-agnostic, the manifest's delivery-mode discriminator and archive-unit abstraction admit a captured segment as a unit, and completeness is defined per unit so a live segment with a disconnect is an incomplete unit, not an undefined state. Sequence-gap tracking is reserved for that initiative; within a purchased historical range the provider's delivery is complete by contract.

- **The third source must not create a third pass shape, and never imports another source** — Two pass frameworks exist today: the EODHD daemon runner and the Kalshi phase/report contract (`PassPhase`, `PhaseReport`, `PassResult`, owned by `data/kalshi/collection_pass.py`). Initiative 120 deferred "daemon framework extraction" to the third source, which is this one. The tick passes follow the Kalshi contract as a *pattern* — the same phase, report, and result shapes, duplicated into the tick package under 120's accept-some-duplication precedent — and import nothing from `data/kalshi`: the dependency direction between two data sources is never source → source, only source → shared foundation. Three copies of one small contract is the evidence that decides whether hoisting it into a shared module is warranted; if it is, that extraction is foundation (9xx) work, not a prerequisite here. A copy drifts: the Kalshi contract has already grown since its first slice (267 added a historical phase), so each 220 slice design diffs the tick copy against the Kalshi original and absorbs what applies — the copy is re-derived per slice, not made once, and the diff is a named task in each slice's task file so it is done and checked off rather than remembered.

- **Operational state has one home; tick data has another** — Run accounting (`pass_runs`) stays where it lives today, in the production TimescaleDB database's minute migration track, for every source including tick: it is the one place `mt data overview`, `mt-run status`, and `/api/v1/overview` read "what ran", and the machinery that closes superseded and abandoned runs (922) operates per database and must not be duplicated. Consequently `PassKind.TICK` lands as a *minute-track* migration that re-renders the `pass_runs` CHECK constraint from the enum (journal 20260901: a served enum grows under you; the applied constraint rejects the new value until a migration re-renders it), never as part of the tick track. The same change gives the new kind its cadence (both are deferred with the cadence decision; until then tick runs are manual and their record is the manifest and ledger): `schedule_for` in `firing_schedule.py` is a deliberately exhaustive ladder that raises on a kind it does not know, so `PassKind.TICK` lands with its branch there — the one place every kind's firing calendar lives, and what `mt-run status`'s next-firing line and the health check read. The tick database holds tick data and tick-data state only — definitions, manifest, hypertable. Every composing surface (overview, health, accounting, status, the API) therefore reaches the tick database through a second connection pool built from `MT_TICK_DB_URL`. Two failures are kept distinct. The setting *absent* from the environment is a misconfiguration. It fails the processes whose job is tick data — the tick passes, and `mt-serve`'s tick endpoints — the way each pass raises today when `MT_TIMESCALE_DB_URL` is unset. The multi-source surfaces (overview, health, accounting, status) instead print a loud `tick: not configured (MT_TICK_DB_URL unset)` line and carry on, so a tick misconfiguration can never silence minute, daily, or Kalshi monitoring; the minute, daily, and Kalshi passes have no tick duty and never read it, so a tick misconfiguration cannot stop them. The tick database *unreachable* is an outage and degrades only the tick surfaces (Technical Considerations, "Serving-layer failure posture"). A silently missing tick line is the failure mode to design out in both cases. The tick pass records its run through the shared pass-run recorder under that recorder's existing best-effort contract (`PASS_RUN_DB_CONNECT_TIMEOUT_SECONDS`: a pass whose bookkeeping database is unreachable still does its work and reports its own result) — no strict mode and no fork of the pass-run machinery. A production-database outage therefore costs a tick run its `pass_runs` row, exactly as it does every other source, and never its money or data: what was bought and ingested is recorded in the manifest and ledger on the tick database regardless. The coupling that remains runs in one direction, tick → production, and has two edges. Tick composing surfaces read the production database for "what ran". The ingest pass reads the CME calendar there: it loads a unit's sessions once, at unit start. So a production outage halts tick *ingest*: units wait in the archive, and nothing is lost or bought twice. Tick *acquisition*, which needs no calendar, continues. The reverse, tick trouble reaching production, is what the isolation goal forbids.

## Envisioned State

A configured **tick universe** — instruments (by product and contract selection rule), schema tier per instrument, and the range each is wanted for — drives two bounded passes and one operator surface.

- **Contract definitions** — For each configured product, the provider's instrument definitions for the wanted range are acquired and stored: contract symbol, provider instrument identifier, expiration, tick size, multiplier, and the identifier's validity window. This is the futures instrument model, and it is populated before any tick data, because tick records are keyed by identifiers only the definitions can resolve.

- **Universe resolution** — The configured universe names either explicit contracts or a product with a provider-side continuous symbol (front-by-calendar and so on). Acquisition resolves product → contract *at the provider*, at request time, and each delivered file's metadata header maps its input symbols to the real contracts' instrument identifiers. Acquisition therefore never depends on local roll machinery, which is a read-time concern built after data exists; acquisition needs only definitions and a request. Historical files carry no in-stream mapping records; that is a live-API feature. Each file's DBN metadata header carries the mappings instead: input symbol → instrument-id intervals, plus the partial and not-found lists (220 slice design; the shipped reader exposes them). This rests on a premise — that those header mappings are complete enough to attribute every tick to its contract — which is a named success criterion of the proof, not a detail to confirm later. The fallback if it fails is stated now: request by explicit raw contract symbols resolved locally from definitions, which costs the same and removes the dependency on provider-side continuous resolution.

- **Acquisition pass** — Reconciles in-flight units first, then computes the wanted set (universe × range) minus the manifest in the provider's own request grain — calendar-day (UTC) ranges, matching how batch files are split — estimates cost and size for the remainder, refuses above the spend ceiling, and otherwise submits batch requests, polls for delivery within its wait budget, downloads the files into the archive, verifies them, and advances manifest rows. Requests are never session-aligned: a session that spans two calendar days is covered by two units, and which units cover which sessions is a ledger fact established at ingest, not a request-time decision. Run manually with a range, it is the backfill and the catch-up; if a timer is adopted (Technical Considerations, "Cadence"), the same command keeps a universe current. Same command, same state. Purchases are **batch jobs only**: a batch file can be downloaded again at no charge for 30 days, while a repeated direct-range request is billed again, and an unknown submit outcome is reconciled against the account's job list rather than re-bought.

- **Adopting existing batch files** — A batch job already downloaded outside the pass (the two free-credit jobs) is adopted into the archive, not re-bought. The adoption reads the job's own `manifest.json`, verifies every file's size and SHA-256 against it, reads the job's record from the provider (free), and writes archive units at *downloaded* with the job's recorded cost, so completeness, accounting, and the 30-day cap treat them like any other purchase. A file that fails verification is not adopted.

- **Ingest pass** — Reads unprocessed archive units, decodes them through the provider adapter, resolves instrument identifiers against definitions, assigns each record its session through the CME calendar's session lookup, and bulk-loads the tick hypertable on the tick database. Resumption is at **unit boundary by design**: a unit's ledger rows and its *ingested* transition commit together, after its last batch, so a pass that dies mid-unit leaves raw rows the next attempt's natural-key conflict-ignore skips and no ledger rows — completeness never sees a half-ingested unit. Re-decoding a partially ingested unit is the accepted cost of that simplicity; the proof measures whether intra-unit checkpoints are *needed*, not whether they are supported.

- **Storage** — A `tick` migration track on the tick database instance. One hypertable for the trades tier — trade fields always present, best-bid/offer fields present when the instrument's tier includes them — with chunk interval set from wall-clock span and any read-side aggregates created per the journal rules. The tier (`trades` or `tbbo`, the provider's own schema names) is a property of the instrument's configuration and is recorded on each archive unit and ledger row; it is never a column on the tick row, because under this model a quote is not an event of its own but an attribute of a trade, and a row whose BBO fields are null is a trades-tier row by construction. **One table, decided (PM, 2026-09-27; architecture review F004):** in practice one tier will be used almost everywhere, chosen as experience shows which is more useful, and the tiers will rarely be mixed. So a tier change over loaded history is a rare, one-off operation: a supersession that deletes and reloads that instrument's history from the archive. Every read surface stays on one table. One table per tier was considered and rejected, because it would make every surface read two tables to support a mixing that will rarely happen. Null BBO fields cost a null-bitmap bit, and near nothing under compression. The tier choice itself is unchanged: `trades` and `tbbo` are both stored tiers, set per instrument, and chosen at the 226 go/no-go. Slice 105's `TickEventType` enum (`trade`/`quote`) and its unit test belong to the discriminator model this replaces; the tick storage track removes them along with 105's stale integration test, and the tier vocabulary is a new enum in the tick package. Because the table is created before the proof measures it, the initial interval is deliberately conservative — on the order of the minute tier's proven geometry, derived from the same rule — so the proof validates rather than invalidates the schema; if it invalidates anyway, the accepted remedy is a rebuild from the archive, which the file-first principle makes a compute cost rather than a repurchase. The definitions, manifest, and ingest-ledger tables live alongside it. Physical grouping by instrument — space partitioning *and* the compression layout (the candidate is segment by instrument, order by event time and sequence) — is one class of decision and is made once, from the proof's measurements on the adopted files, not inherited from the 105 outline: per-instrument row counts for a liquid front contract and a thin deferred one differ by orders of magnitude, which is where a single global choice hurts.

- **Operator surface, at minute parity** — Every verb the minute tier answers has a tick-tier answer: status (per product and contract: sessions complete, pending, failed; the active contract per roll rule and the next roll), coverage per session, `pull`/backfill and ingest, `get` for ticks and for bars derived from ticks (by contract or by product-plus-roll-method), health and accounting lines, and debug reads of manifest and definitions. It is an `mt data tick` subgroup (the Kalshi shape), decided and shipped by slice 220 and recorded in the data-correctness contract's I10 row; the constraint is that the same questions are answerable with the same defaults. `mt-run tick` and `mt-run follow tick`, a `tick` row in `mt-run status`, `PassKind.TICK` in `pass_runs`, and a tick line in `mt data overview` — reachable in production as `mt-run data overview` — complete the picture. Process status from systemd, data status from persisted state — the two layers the 2026-08-23 ADR requires.

- **Serving surface, at bars parity** — The API serves ticks and tick-derived bars for a contract or for a product under a named roll method, the contract catalog (definitions, expirations, the active contract per rule), and tick freshness and coverage in `/api/v1/status` and `/api/v1/overview`. Both reference documents (`docs/api/reference.md`, `docs/api/agents.md`) cover the new endpoints under the 190 documentation gate, and `openapi.json` is regenerated at each slice close.

- **Backup and restore** — The archive directory and the tick database are enrolled in the 915/920 regime: the archive in the backup set as data, the database with a policy chosen from measured rebuild cost, both exercised by the restore drill. Retention, exclusions, and host placement are recorded in the backup runbook, not only here.

- **Validation loop** — Every ingest verifies each unit with checks that cost nothing to buy; no provider data is purchased for validation (PM direction 2026-09-23). *Counts*: the provider's record count for the unit — reported with the batch job and by its free record-count query (verify at slice design) — equals the records decoded, and after the load the raw table holds exactly those records for the unit's range, whether written now or by an earlier attempt. That proves the decode dropped nothing and the projection wrote everything. *Resolution*: every record resolves to a contract through the stored definitions; an unresolvable identifier fails the unit rather than loading an unattributed row. *Session boundaries*: every trade falls inside a session in the calendar — never in the daily break, on a closed day, or outside the calendar's populated range — and one that does not is a session-model defect. The checks run before the unit's ledger rows and its *ingested* transition commit: a unit that fails one moves to *failed* with the check named, contributes nothing to completeness, and status shows it. What these checks cannot prove is price correctness against an independent source. With one provider and no purchased companion data, no such source exists within scope — the same fact that makes I7 unsatisfiable (Technical Considerations, "Data-correctness contract amendment"). Prices are decoded by the provider's own library from its own fixed-point values and preserved without reinterpretation, and that is the extent of the claim.

**Completeness definitions** (the analogue of 120's caught-up and 260's complete-market definitions), stated at the grain the manifest actually has. Provider files are split by calendar day and hold many instruments, so a unit's record count says nothing about one instrument-session; the join is made once, at ingest, when the decoder sees every record anyway: ingestion writes an **ingest ledger** row per *(instrument, session, unit)* — records loaded, first and last event time, traded volume — and status reads that ledger, never re-decoding. A CME session spans two calendar days and so two day units. Each unit writes only its own part of the session, which keeps the write idempotent: a re-ingest replaces that unit's rows and never adds to another unit's. Session totals are summed at read time over the session's current units, excluding superseded ones. The same grain lets a session be written by more than one source (Technical Considerations, "Realtime paths"). The rows a unit writes are determined by its range, not by the records it happened to contain: for every configured instrument whose definition is valid in a session the unit's range touches, ingest writes a row, including a zero-record row (no event times) for a session part in which the instrument never printed. A quiet session on a thin deferred contract is therefore *complete with zero records*, not missing forever, and "caught up" stays reachable. An *archive unit is complete* when its state is *ingested*. An *instrument-session is complete* when every unit covering it is complete and the raw table's count for that instrument-session equals the sum of its current units' ledger counts. The *universe is caught up* when every configured instrument is complete for every session in its wanted range up to the **availability edge**, which is not a local rule: each pass records the provider's free dataset metadata — the dataset's available range and its per-day condition (available, pending, degraded, missing) — The provider reports conditions per calendar day, and a session touches two days, so a session takes the worst condition of the days it touches, in the order *missing* > *degraded* > *pending* > *available*. A session is therefore *pending* if any day it touches is pending and none is worse, and *missing* or *degraded* is surfaced as such. A session whose days' metadata cannot be fetched is *edge unknown*. A missing day is also where a unit's `PROVIDER_HOLE` comes from. The measured lag of about 8 hours is the expected distance behind the edge, used to flag an edge that stops advancing; it is never used to infer that a session is missing.

At completion, a small ES (then GC) tick history sits in the archive and the database, every number the realtime initiative and the tick-serving work need has been measured on it, and expanding the universe is a configuration edit followed by a cost estimate — one that includes any roll-method inputs the added range needs, since figures derived from ticks exist only for sessions already bought.

## Technical Considerations

- **Schema tier is the cost decision** — The three candidate tiers differ by what triggers a record: a trade (`trades`), a trade plus the book state just before it (`tbbo` — same record count as trades, wider records), or every top-of-book change (`mbp-1` — many times the record count for a liquid contract). Slice design must obtain billable size for each tier over the *same* ES range from the provider's free estimation endpoints before the first purchase, and record the numbers; the tier choice, and whether GC follows at the same tier, are made from those figures. Record sizes and per-session volumes are to be verified from Databento's schema documentation and measured, not assumed.

- **Delivery mode and retention** — Databento serves history two ways that yield identical data: a direct range request streamed into the client, and an asynchronous batch job that produces files (split by day by default, zstd-compressed) retained for a limited window and downloadable within it. The file-first principle points at batch for anything that will be archived, and the cost of repeating a request settles it: purchases are batch jobs only (Envisioned State, "Acquisition pass"). The adapter's direct-range method stays for small probes but no pass calls it. Retention is **30 days after the job finishes processing**, measured on all seven of the account's jobs (220 slice design); no per-mode size limit is published in any source readable so far. The window is a deadline, and "the next pass runs before it" is not a guarantee — a disabled timer or a host outage breaks it — so four things make it one. *Ordering*: the reconcile phase downloads every deliverable unit, earliest deadline first, before it estimates or submits anything new; downloads are free and submissions cost money, so that order is always right. *Explicit expiry*: a unit whose deadline passes undelivered transitions to *failed* with reason *retention expired* and re-enters the wanted set; its repurchase is a new unit whose manifest row names the expired one, so the repeat cost appears in the estimate and the accounting rather than vanishing into a retry. *Escalation*: the health check (919) reports any in-flight unit whose deadline falls before the tick pass's next scheduled firing (`schedule_for`, the same source `mt-run status` reads) as a finding that needs a human, and the operator runs the pass by hand. *Cadence bounded by the window*: whatever cadence is adopted must leave a submitted job's 30-day window covering several consecutive missed runs. *Manual regime, until a cadence exists*: a pass that submits does not exit with units in flight. It polls until its jobs deliver and downloads them in the same run. The account's seven jobs took 5 s to 84 s from submit to done (1.4 GB `tbbo` in 57 s), so the wait budget is minutes, not hours. A job still running when the budget ends is printed loudly with its deadline, and downloading it by the deadline is then the operator's responsibility. Because nothing is bought until the Standard plan is subscribed, no purchase can sit in flight while 923 or any other gate waits. The adopted free-credit files have no retention window at all.

- **Availability lag and licensing** — Historical access lags the market by about 8 hours (measured 2026-09-27; see Architectural Principles, "Pass form"). Historical data needs no license. Intraday and realtime need a live plan plus CME's pass-through license fee.

- **Sourcing sequence and plan** (PM direction 2026-09-27) — Data comes from three sources, in order:
  1. The two free-credit batch jobs already on disk, adopted and verified (Envisioned State, "Adopting existing batch files"). They prove storage, ingest, and the proof slice for almost no spend. They hold no `definition` records, and definitions are billable, so they go through the estimate → guard → manifest path like everything else. The proof therefore buys the definitions for its ranges (under $0.01 for six months of ES) after the PM sets both ceilings.
  2. Databento's **Standard plan** for CME Globex ($199/month), subscribed when more data is needed, ideally not before realtime work begins. Per the PM, it includes every schema except MBP-10 and MBO, so `tbbo` is included; 12 months of L1 history (which includes `tbbo`); 1 month of L2/L3 history; 16 years of L0 (`ohlcv-*`) history; and 16 years of `definition` and `statistics` (including open interest). The included year is taken first.
  3. Purchases outside the plan, which are rare: for example, studying an older period such as the COVID era, possibly from 1-minute OHLCV instead of ticks (undecided).

  Whether plan-included history comes through the same historical API and prices at $0 in `get_cost` is verified at subscription. The subscription is the recurring cost, so once it starts the initiative moves at a sustained pace.

- **Cadence** — Deferred (PM direction 2026-09-27). No schedule code is built until realtime work makes the cadence decidable: no timers, no `schedule_for` branch, no `PassKind.TICK` firing calendar. Until then every tick pass runs by hand. There is no daily history pull; runs are on demand. The inputs are: the 8-hour availability lag; the 30-day retention window; the realtime initiative taking over the steady state; and catch-up after a realtime gap needing a bounded, manually triggered path. `schedule_for` requires every `PassKind` to declare its firing calendar, so a manual-only tick pass needs an explicit "no timer" answer there, not an omission.

- **Realtime paths** (PM direction 2026-09-27) — The realtime initiative will decide how recent history is produced. **Path A** assembles it from the realtime capture. **Path B** takes it from the historical API with its ~8-hour lag. Neither is chosen now, but no 220 decision may rule one out without saying so. Every 220 slice design carries a short "realtime paths" check naming any choice that forecloses either path. Three choices kept both open at the 2026-09-27 revision:
  - the per-unit row identifier;
  - the supersession rule, historical-over-live by default;
  - the per-unit ingest-ledger grain.

  Other choices are neutral to the paths: the delivery-agnostic natural key, the manifest's delivery-mode discriminator, and completeness per unit.

- **Futures identity and symbology** — Databento resolves symbols four ways: raw contract symbols, dataset-scoped numeric instrument identifiers, parent symbols covering a whole product (including spreads), and continuous symbols (`.c`, `.n`, `.v` — calendar, open-interest, and volume roll rules — with a depth index). Continuous symbols are a *request* convenience that maps to real contracts over time; the data carries the real contract's identifier. The instrument model must therefore store definitions and their validity windows, treat identifier reuse as expected, and derive continuous views from stored rules. Exact roll semantics and the mapping-message behaviour in delivered files are slice-design verification items.

- **Session model** — CME's trading day, daily break, Sunday open, and holiday schedule define the session boundaries that coverage, completeness, the ingest ledger, and the session-boundary check all depend on; the equities calendar does not describe them, and the model is load-bearing enough that its shape is fixed here rather than at slice design. It is data in the calendar tables I4 already governs, not a parallel code path — I4's own text is one function, with hours and holidays "handled by data in the calendar table". Its home is the production database's existing calendar tables (`trading_calendars`, `trading_holidays`, `trading_sessions`, minute migration track), keyed by `calendar_id` and holding `NYSE` today; placing it in the tick database instead would make every I4 consumer route per calendar across two pools and grow slice 923 a session-routing scope. It has three pieces. The *calendar row* is the trading-hours schedule: one `calendar_id` per distinct CME schedule (ES and GC both trade Sunday–Friday 17:00–16:00 Chicago time, so one row serves both — verify per product at slice design), with timezone, open, and close. A session is one contiguous open-to-close interval identified by its CME trading date, the date it closes, and the daily break is the gap between consecutive sessions, not a hole inside one; a product with an intra-session halt does not fit and is out of scope until one is configured. The *session rows*: `trading_sessions` already stores open and close as timestamps under a `(calendar_id, session_date)` key, so a Monday session that opens Sunday evening is representable as the table stands. The population logic (`populate_trading_sessions`) is what cannot produce it, because it combines open and close with the same calendar date. It gains one rule, for every calendar: an open time later than the close time means the session opens on the previous calendar day. `NYSE` opens before it closes, so its rows are unchanged, and the existing Monday–Friday trading-date loop is already right for CME, whose Sunday-evening open belongs to Monday. The *exceptions* — holidays, early closes, and exchange-declared irregular sessions — are `trading_holidays` rows under the CME calendar, seeded by a minute-track migration from CME's published schedule, which is public and free; whether it reaches back over the whole wanted range is a slice-design verification item. No purchase is required. Session lookup for a tick is a method on `TradingCalendar`, the I4 surface, answering which session contains a timestamp from those rows; the ingest pass loads a unit's sessions once and assigns records in memory. It is not a pure function and does not pretend to be one: a timestamp outside the populated range is an explicit failure (the session-boundary check), never a guess, so the calendar is populated backward over the wanted range as part of the seed, and forward by the same per-calendar extension that keeps `NYSE` current (`TRADING_SESSIONS_EXTENSION_YEARS`, `mt data extend --calendar`, and the automatic extension `mt data status` runs). The tick ingest pass does not rely on the minute tier to run that extension: before loading a unit's sessions, it runs the same shared extension for the CME calendar when the unit's range reaches past the populated horizon. A range still outside the populated horizon after that is the explicit failure, never a guess. The open-after-close change to `populate_trading_sessions` is guarded by a regression test that `NYSE` rows are unchanged (slice 221). The calendar is shared reference data, not tick data — the second carve-out from the isolation axes alongside run accounting (Design Goals). Hard-coded CME hours anywhere else remain the defect I4 names. The design carries its own proof: wrong boundaries put ingested trades in a break or on a closed day, which the ingest pass checks on every unit (Envisioned State, "Validation loop"). The calendar's values and seed are slice-design verification items; the representation is not.

- **Database placement and roles** — `MT_TICK_DB_URL` exists but points nowhere. A separate instance can mean a second database on the production cluster, a second cluster on the production host, or a second host; each has a different answer for memory contention with the minute tier, for backup (915) and least-privilege roles (913), and for the test cluster (917). Two constraints apply to all three. First, composition is cross-database under every option — PostgreSQL does not join across databases — so overview, health, accounting, status, and the API server (built today around one URL, `create_app(db_url=…)`, 187 D9) each gain a second pool from `MT_TICK_DB_URL`, and that variable must be present in the service environment file of every process with a tick duty (Architectural Principles, "Operational state has one home"); the tick pass writes its run row to the production database through the shared recorder. The migration CLI is single-database today (`migrate apply` resolves one maintenance URL, and its own comment records that every track targets the same database), so a tick track on another instance needs track → URL routing, a second migration ledger, a second maintenance credential with its own grant artifact under 913's separation, and a cold-start path (`mt data init`) that knows two databases. That touches every migration and credential code path, which is foundation work, not tick work: it is slice 923 of the foundation-cleanup plan, sequenced before the tick storage track (Anticipated Slices). Second, the parity goal's isolation claim disqualifies any placement in which a filling tick volume or a runaway tick query can take down production storage — a shared cluster or host needs a separate volume and a resource bound, or it is not a candidate. The decision is the PM's, informed by the 220 preflight's per-tier size estimates (for example, six months of ES `tbbo` bills at 4.6 GiB uncompressed) and by the compressed size measured when the adopted files are loaded into a throwaway database on the test cluster; the architecture requires that the tick track never shares a hypertable, chunk geometry, or refresh policy with the minute tier.

- **Cross-source arbitration** — 916 supervises each source independently and installs `manta-acquisition.slice` with no resource settings, because the numbers were speculative until there was measured contention; 260 inherited the gap and named this initiative's tick volume as what makes it real; the 900 plan's Future Work records that the solution belongs to the initiative that brings the new sources, not to maintenance. It belongs here, then, and it is answered in two steps that follow the prove-first structure. Before the proof, the mitigation is the one 916 already uses: the tick pass's firing calendar is chosen to stagger against the minute pass's known firing times, and bounded ingest batches make the tick write load steady rather than bursty. The proof then measures the contention itself — the tick ingest pass running concurrently with the minute pass, recording the minute pass's duration and the host's I/O, memory, and database write throughput against its solo baseline. The steady-state slice sets `IOWeight`/`CPUWeight`/`MemoryMax` on the slice from those numbers and chooses among the three mechanisms the 900 plan lists — a resource-class lock the passes take, a scheduler inside `mt`, or calendar stagger kept as-is — on that evidence. Setting weights before the measurement would repeat the mistake 916 declined to make.

- **Ingest throughput and the write path** — Bulk load through `COPY` into a hypertable is the candidate path; its rate on tick rows is re-measured by the proof, never recalled from the minute tier's figures (journal 20260720: recorded numbers are re-measured, not recalled). Tick sessions are far larger than minute days; decode cost (the provider's Rust-backed decoder versus per-record Python), whether that decoder releases the interpreter lock (which decides threads versus processes for the adapter's execution model), batch sizing, and whether unit-boundary resumption's re-decode cost justifies intra-unit checkpoints are measured there too. The measurement has a pass/fail, restated for on-demand acquisition: a day's sessions for the configured universe must ingest far faster than a day of market time, so a catch-up after a gap converges, and a month of sessions (the plan's included year, taken a month at a time) must ingest within an operator's working session.

- **Active contract and roll methods** — Calendar (expiration-based, possibly with a configured offset of days before expiry), open-interest, and volume rules each need different inputs: calendar needs only definitions; open-interest and volume need per-contract daily figures. Open interest is not derivable from trades at all and comes only from the provider's `statistics` schema. The Standard plan includes 16 years of it, so the open-interest rule is no longer blocked on a purchase. It must be evaluated when roll methods are designed (PM direction 2026-09-27: "something we should not forget to look into"). `statistics` units come in through the same archive, manifest, and ingest path as any other schema. Volume comes from ingested ticks (free, but only for sessions already bought), and it is not an aggregate: the ingest ledger already holds one row per instrument-session written at unit commit, so it carries the session's traded volume alongside its record count, and volume-rule inputs are read from the ledger. Nothing refreshes, so nothing can stall, and no request scans the raw table. These figures feed read-time resolution only — which contract a product-level read or status line names — never acquisition, which resolves contracts at the provider (Envisioned State, "Universe resolution"); journal 20260725 rule 2 is kept by construction, and every answer that names an active contract also names the latest session its rule's inputs cover. The rule vocabulary must match the provider's continuous-symbol conventions closely enough that a request phrased in either resolves to the same contract on the same day, and the resolution must be reproducible: a status line or API response that names the active contract can be re-derived later from stored definitions and stored figures — which means purchased figures, if statistics are ever bought, are archive units with manifest provenance like any other purchase, and derived figures are ledger values recomputable from the raw table by re-ingest. Because derived figures exist only for sessions already bought, expanding a universe backward carries the cost of roll inputs for the old range, and the estimate says so. Roll-day handling (the session on which the rule switches, and whether both contracts' ticks are served across it) is a slice-design decision with a stated default.

- **Own subgroup or granularity switches** — Decided by slice 220 (its Technical Decision 3): an `mt data tick` subgroup, and a `/api/v1/futures/*` API namespace, one decision covering both surfaces. `mt data overview`, `health`, and `accounting` gain tick lines in place. 229 and 230 apply the decision and do not revisit it.

- **Backup coverage** — The archive is the recoverable source of truth and is backed up as data. The database projection's policy — full base-backup weight, WAL-only, or rebuild-from-archive on restore — is chosen from the rebuild cost the proof measures, and the restore drill proves whichever is chosen. If the tick database lands on a second host or cluster, the 915/920 tooling (base backups, WAL archiving, keep-days, exclusions) is extended to it rather than duplicated by hand; the same applies to the 913 role set.

- **Serving-layer failure posture** — The API's lifespan opens its pools eagerly and fails at startup if the primary database is unreachable (187 D9's `create_app(db_url=…)` exists so the load tier never reads the production URL from the environment). Copying that posture for the tick pool would let a tick-instance outage stop `mt-serve` from starting — the parity goal defeating the isolation goal. The decision: `mt-serve` starts without the tick database; the tick pool is opened at startup but its failure is recorded, not raised; tick endpoints answer `503` with the API's existing error shape while the pool is down and recover when it returns, through the pool's own reconnect with no retry loop of ours; `/api/v1/health` reports the tick pool the way it already reports the primary — always HTTP 200, with a tick-database field beside the existing `db` field (`ok` or `error`) — so a caller reads the tick state from that field, and a down tick pool never makes the process itself look down; equities routes never consult it. This is a new posture for the codebase, chosen deliberately for one class of surface, and `create_app` gains a `tick_db_url` seam so the load tier's discipline covers tick endpoints too. The same split applies to `mt data overview` and `health`: a tick line that reads "unreachable" is the correct output, not an omitted line.

- **Data-correctness contract amendment** — The contract is normative and says this initiative inherits I2–I10 and adds tick-specific invariants "when initiative 200 lands"; adding them is a deliverable here, not an afterthought. Because the contract holds that a guarantee no shipped slice covers is broken, the amendment is not one late slice's task. The first slice that touches a governed surface — the session model's second calendar behind I4 — lands the amendment's frame: the tick invariants, the I7 exception, and the vocabulary rules. Every later slice adds its own rows to the contract's slice-mapping table as it ships, which is the contract's standing rule for every slice. The contract also attributes sequence-gap detection to this initiative, and this document reserves it for the realtime initiative, since within a purchased historical range the provider's delivery is complete by contract. The amendment records that move and its reason rather than leaving the two documents disagreeing. Three points are settled now. **I4** (exactly one trading-session function in the codebase): the futures session model is a second *calendar* served through the same single session-query surface, never a second function — hard-coded CME hours anywhere are the defect I4 names. **I7** (independent cross-vendor audit): unsatisfiable for tick by this initiative's scope — one provider, no cross-venue consolidation — and the ingest checks (counts, resolution, session boundaries) are *verification* in the contract's vocabulary, not audit — no independent price source exists within scope, and none is bought; the amendment records the exception rather than letting the contract claim what the scope cannot deliver. **Vocabulary**: tick completeness is manifest-based, not `acquisition_state`-based. `Granularity.TICK` already exists in `data/acquisition/state.py`, from 120's acquisition-state vocabulary, with no data behind it; it is the one tick member of that enum, distinct from `PassKind.TICK`, which names a run, not a granularity. `granularity = 'tick'` enters the minute track's enumerations (`data_gaps`, `data_status`) only where a surface actually reads them; the amendment lists which.

- **Relationship to 240 (flat-file import)** — 240 is a generic import tool for CSV/Parquet/provider exports into the existing acquisition-state universe. 220's archive → manifest → ingest shape is the more general pattern; 240 should instantiate it for other formats rather than 220 borrowing from a tool that does not yet exist. DBN decoding stays inside 220's provider adapter.

- **Relationship to the serving API (180)** — 180's exclusions deferred tick endpoints until tick storage exists; this initiative supplies both the storage and the endpoints, closing that exclusion. 180's standing design question — "does this belong in the API?" — is answered per endpoint at slice design, with the futures session model and roll methods as inputs, and 190's documentation gate is the acceptance check.
