## Migration / Refactoring Slices

4. [x] **(903) Deprecated Code Removal and httpx Migration** — Delete `market/deprecated/` directory and all imports from it. Remove old CLI entry points (`ohlc.py` direct invocation, `newsoptions.py`). Replace aiohttp with httpx in AlphaVantage client. Wire existing daily pipeline (`marketdb.py`, `marketservice.py`) into new CLI as `mt data daily` subcommands. Dependencies: [900, 902]. Risk: Med. Effort: 3/5

5. [ ] **(905) Lint and Type-Checker Debt Remediation** — Slice 166's code review landed the mandated `[tool.ruff]`/`[tool.ruff.lint]` config (`E,F,W,I,UP,BLE,ASYNC,B`) and a `[tool.mypy]` block in `pyproject.toml`; activating it exposed **1,730 pre-existing violations across `src/` and `test/` (752 autofixable)** that had never been mechanically gated (re-measured 2026-07-27: **1,706 ruff, 739 autofixable** — the drift is slices closing since). This slice drives that count to zero so the config gates all code, not just new code by review convention. Scope: (1) apply the ruff autofixes and verify no behavior change (per-subpackage test runs); (2) manually triage the remainder — **note that some findings are latent runtime bugs, not style**: the sweep includes `F821` undefined names in `cli/commands/data.py` (e.g. `datetime`, `psycopg` referenced in code paths where they are not imported — a `NameError` waiting on those paths), plus `F401` unused imports, `E402` late imports, `E501` line lengths, and any `BLE` blind-except violations, each fixed or explicitly `noqa`'d with an inline justification per the exception-handling rules; (3) sweep `raise ... from exc` (B904) across the legacy handlers noted in the 166 review; (4) drive `uv run --extra dev mypy` to zero — **97 errors across 20 files** as measured 2026-07-27, worst offenders `market/csv_export_service.py` (28), `cli/commands/provider.py` (23), `cli/commands/data.py` (15); (5) **widen and tighten the mypy gate**, see below. Latent-bug fixes (F821 class) get their own commit(s) with a note distinguishing them from mechanical style fixes.

**Type-checker decision and gate scope (PM, 2026-07-27).** The project stays on **mypy**, not pyright — the python rules say "`pyright` (preferred) **or mypy**", and `pyproject.toml` records the mypy choice as a deliberate slice-166 code-review resolution. Switching tools mid-cleanup would re-triage the same debt twice for no gain; revisit after this slice, not during it. Two real gaps in the gate as currently configured, both this slice's to close:

- **Scope.** `[tool.mypy] files` is `["src/manta_trading"]`, so `test/` is unchecked. The python rules include test code in type checking specifically *because bugs in tests can mask bugs in code* — borne out on 2026-07-27, when a defect **in a test** (`test_cagg_freshness.py` froze the wall clock by monkeypatching a name that `_evaluate` had bound as an import-time default) silently disabled a freshness assertion and surfaced only when the fixture date aged past a threshold and broke the suite on a calendar boundary. Extend `files` to cover `test/` and drive that to zero too.
- **Strictness.** The block sets only `python_version` and `ignore_missing_imports`. A non-strict zero is a hollow number against a rule that calls zero errors a merge blocker, and enabling strict afterward reopens the debt immediately. **Ratchet within this slice** (PM ruling): reach zero non-strict first, then turn strict flags on incrementally and clear each wave, so the slice ends genuinely strict-clean rather than nominally clean. Expect the count to grow substantially when strict lands — that growth is in scope, and re-estimating effort once its true size is known is expected rather than a scope breach.

Verifiable: `uv run --extra dev ruff check src/ test/` reports zero violations; mypy passes over **both** `src/` and `test/` with the strict flags this slice lands; all per-subpackage test suites pass unchanged; the F821 code paths are exercised by at least a smoke test or documented as dead code and removed. Note for slice 907: its pipeline runs `ruff → mypy → pytest`, so whatever gate this slice lands must be mirrored there. Dependencies: [166]. Risk: Med (BLE and F821 triage touches many files; behavior must be preserved except documented latent-bug fixes; the strict ratchet's true size is unknown until non-strict zero is reached). Effort: 3/5

6. [ ] **(906) `mt data` CLI Module Decomposition** — `cli/commands/data.py` is 3,371 lines, >10x the ~300-line guideline, because eight Typer sub-apps (`data` root, `caggs`, `ca`, `instruments`, `lists`, `daemon`, `migrate`, `calendars`) were appended to one module rather than each getting its own. Flagged as F009 in the slice 163 review and deferred; slice 168's review established that over-guideline length is only excusable when the excess is not code — `data.py`'s excess is executable code, so it isn't. Split into a `cli/commands/data/` package, one module per sub-app plus `_shared.py` for the cross-group helpers, with `__init__.py` assembling the Typer tree and re-exporting `data_app` so `cli/app.py` is untouched. Generalizes the existing `universes.py` precedent, which already lives outside the module and is attached via `add_typer`. Strictly behavior-preserving: no signature, help-text, output-format, or exit-code changes, verified by diffing pre/post `--help` captures for all nine sub-apps. Pushing SQL and formatting logic down out of the oversized command bodies (`data_pull` 244 lines, `caggs_status` 202, `data_get` 192) is explicitly follow-on work, not this slice. Depends on 905 so that slice's `F821` latent-`NameError` findings in this exact file are fixed while the code is still in one place, rather than scattered across ten new modules mid-triage. Dependencies: [905]. Risk: Low (mechanical move; live-daemon entry point `daemon run` requires a real prod invocation to verify). Effort: 2/5

7. [ ] **(907) CI Pipeline and Load-Test Gating** — The repo has **no CI**; `.github/workflows` does not exist, so ruff, mypy, pytest, and the `test/load/` NFR tier all run only when someone remembers to locally. Slice 146 added two load tests gated on `MT_RUN_LOAD_TESTS=1` whose docstrings say "CI must enable" — nothing ever did, so those NFR assertions have never run automatically. Slice 167's task review (F002) caught the identical claim being made again for its sub-second `data_status` load test; the PM ruled the CI work out of 167 and into this chore rather than ship a second NFR with an aspirational gate. Scope: workflow config running ruff → mypy → pytest per-subpackage on push/PR — **mypy must run over both `src/` and `test/` with whatever strict flags slice 905 lands** (905 widens and ratchets that gate; CI mirroring the old `src/`-only non-strict invocation would silently under-enforce it) — plus a load-tier job setting `MT_RUN_LOAD_TESTS=1` so the 146 and 167 NFRs get a real gate; decide per-suite whether DB-dependent tests get an ephemeral service container or a recorded skip; quarantine the known pre-existing failure baseline (2 failures + 12 live-DB errors) so a green run means something; retire the "CI must enable" docstrings. Must respect the broken whole-`test/` collection (missing `__init__.py` — per-subpackage invocation) and must never be able to reach the production DB at 192.168.1.144, where the daemon runs continuously. Explicitly excludes new tests, threshold changes, and fixing the baseline failures. Dependencies: [905]. Risk: Low (additive; no production code paths touched — the risk is a pipeline that goes red on day one and gets ignored, which the baseline quarantine addresses). Effort: 2/5

## Integration Work

8. [x] **(904) Packaging and Version** — Completed incrementally across slices 900–903: `uv.lock` committed, `mt` entry point wired, `mt --version` implemented, `pip install -e .` and `uv sync` verified. No standalone slice design needed. Dependencies: [903]. Effort: 0/5

9. [ ] **(908) PyPI Distribution and Production Cutover** — Slice 904 established packaging but no *distribution*: there is no way to install `mt` except a source checkout ([README.md:13](../../../README.md)), and no way for an installed user to learn a new version exists. As of the 2026-08-01 audit, PyPI holds `manta-trading` at version `0.0.1` ("Manta Trading - placeholder package") — a name reservation intended for a future full product, **not** this data package — while the repo is at 0.5.0; the v0.5.0 tag is pushed but `gh release list` is empty, so the release is invisible to anyone not reading `git tag`. Production (.144) compounds this: [production-deploy.md](../runbooks/production-deploy.md) Phase 4 installs by `git clone` into `/opt/manta-trading` + `uv sync`, and both systemd units hard-code that checkout (`WorkingDirectory=/opt/manta-trading`, `ExecStart=/usr/local/bin/uv run mt …` — [mt-minute-daemon.service.tmpl:11-14](../../../deploy/systemd/mt-minute-daemon.service.tmpl), same in the daily unit), so no package-manager upgrade can ever reach it; that runbook is also first-install-only, with no upgrade procedure at all, and its migration step still passes the `--db all` flag retired with the single-DB consolidation in slice 152. **Scope:** (1) rename the *distribution* to `manta-trading-data` (verified available on PyPI 2026-08-01; the import package `manta_trading` deliberately stays put — slice 911 renames it separately, invisibly to users) and replace the hard-coded `importlib.metadata.version("manta-trading")` lookup at [cli/app.py:36](../../../src/manta_trading/cli/app.py) with a single named constant, since a distribution-name string scattered in code fails silently on rename; (2) build and publish sdist + wheel via `uv publish` using a scoped API token — PyPI has no project-creation UI and "pending publishers" explicitly do *not* reserve a name, so the first successful upload is what claims it; rehearse against TestPyPI first, as this artifact becomes production's install path; (3) adopt `gh release create` per tag with the CHANGELOG section as the body, backfilling v0.5.0, giving watchers and the `/releases.atom` feed a real notification channel; (4) cut .144 from checkout to `uv tool install manta-trading-data==X.Y.Z`, rewriting both systemd templates to invoke the tool-installed `mt` with no working-directory coupling; (5) add the missing **upgrade** procedure to the deploy runbook (stop daemons → upgrade → `mt data migrate status` → apply → restart → verify) and fix the stale `--db all` flag. Explicitly excludes trusted publishing and automated release workflows, which need CI (907) and can convert later without disturbing the published name. Verifiable: `uv tool install manta-trading-data` into a clean environment yields a working `mt` whose `--version` matches the published version; the v0.5.0 and current releases appear in `gh release list`; .144 runs both daemons from the tool-installed entry point with no `/opt/manta-trading` checkout on the `ExecStart` path; the upgrade runbook is executed end-to-end from the installed 0.4.0 rather than described. Dependencies: [904]. Risk: Med (touches the continuously-running production daemon; the PyPI upload is irreversible per version). Effort: 3/5

10. [ ] **(909) `mt update` Self-Update Command** — Once 908 makes releases installable, an installed user still has no in-tool way to discover or apply one; `mt --version` reads `importlib.metadata` and never consults a registry. Port the shape proven by `cf update` (~187 lines, `context-forge/packages/cli/src/commands/update.ts`): query the latest published version, compare, detect how the tool was installed, and shell out to the matching upgrade command. **Scope:** (1) fetch `https://pypi.org/pypi/manta-trading-data/json` → `info.version` with a bounded timeout, returning nothing rather than raising on any failure (network, non-200, malformed) so a registry outage never breaks the command; (2) compare with `packaging.version` — declared as an explicit dependency, not relied on transitively — rather than hand-rolled string splitting; (3) detect install method and auto-upgrade only the blessed `uv tool install --upgrade manta-trading-data` path, printing the correct command for pipx/pip-user installs and refusing outright on an editable or source-checkout install (the state every developer machine is in today); (4) `--json` as a pure query with no side effects, `--yes` for non-interactive use, and non-TTY-without-`--yes` reporting rather than acting. **The command must never touch the database.** After a successful code upgrade it reports the pending-migration count and points at `mt data migrate status`; that check is best-effort and a failure to reach the database must not fail the update. The registry call happens only when the command is invoked — never at CLI startup. Verifiable: unit tests cover up-to-date, update-available, unreachable-registry, and each install-method branch with the upgrade call mocked; `--json` output is asserted side-effect-free; a real end-to-end upgrade is performed between two published versions. Dependencies: [908]. Risk: Low. Effort: 2/5

11. [ ] **(910) Schema-Change Transparency and Confirmation** — An operator upgrading `mt` needs to know *before* running anything whether it will alter production database structure, and how severely. Today it cannot be known without reading SQL: migration records are `{id, description, sql}` ([market/schema/migrations/minute.py](../../../src/manta_trading/market/schema/migrations/minute.py)) with no impact classification, so in `mt data migrate status` a bare `CREATE TABLE` and a rewrite of the 4.4-billion-row `minute_ohlcv` hypertable render identically; and `mt data migrate apply` ([cli/commands/data.py:177](../../../src/manta_trading/cli/commands/data.py)) takes no dry-run, no plan preview, and no confirmation — it simply applies everything pending. **Scope:** (1) add an impact classification to the migration record as an enum (additive / rewrite / destructive) per the no-scattered-comparison-values rule, never a bare string, with optional operator notes carrying the concrete cost ("rewrites `minute_ohlcv`, ~4.4 B rows"), backfilled across the existing chain in both tracks; (2) render impact alongside description in `mt data migrate status` so the preview answers "how bad is this" without opening source; (3) give `mt data migrate apply` a plan-then-confirm gate — print the full pending plan, require explicit confirmation when any pending migration is non-additive, `--yes` for automation, `--dry-run` for inspection — and mirror the gate in `mt data init`, which shares the same apply path; (4) a version-skew guard so that when the installed build expects migrations the database has not applied, commands depending on the new schema fail naming the gap rather than surfacing a raw SQL error. This generalizes the requirement so it holds for every future release, not only the 908 cutover. Verifiable: unit tests assert the confirmation gate blocks a non-additive plan without `--yes` and passes an additive one; `--dry-run` applies nothing (asserted against migration state before and after); every migration in both tracks carries a classification; the skew guard's message is asserted to name the missing migration ids. Dependencies: none — may deliberately precede 908, since the .144 cutover is itself the first upgrade that would benefit from the gate. Risk: Med (touches the schema runner every deployment depends on). Effort: 2/5

12. [ ] **(911) Import-Package Rename to `manta_trading_data`** — Deferred half of the 908 naming decision. With the distribution published as `manta-trading-data` but the import package still `manta_trading`, this package would collide on disk with the future full product if that ever ships the same import root; the PM's decision is to rename rather than reserve a different root for the future package. Purely internal — the distribution name, the `mt` entry point, and every user-facing surface are unchanged, so an installed user upgrading across this version notices nothing. **Scope:** mechanical move of `src/manta_trading/` → `src/manta_trading_data/` with all imports across `src/` and `test/` updated, the `[project.scripts]` entry point target adjusted, and the distribution-name constant introduced in 908 left untouched. Strictly behavior-preserving: no signature, output-format, or exit-code changes. Best sequenced after 906 splits `cli/commands/data.py`, to avoid renaming imports in a 3,371-line module that is about to be decomposed. Verifiable: all per-subpackage test suites pass unchanged; `grep -r manta_trading\\b` over `src/` and `test/` returns nothing outside the new name; a clean `uv tool install` of the resulting build produces a working `mt` at the same version. Dependencies: [908]. Risk: Low. Effort: 2/5

## Notes

- Slice 900 is the largest because it establishes both CLI and config systems together — they're co-dependent (CLI needs config for setup, config needs CLI for management commands). Splitting them would create circular dependencies.
- Slice 903 carries medium risk because the deprecated code removal touches the main entry point and the httpx migration changes the HTTP layer. Both are well-scoped but affect working functionality.
- The daily pipeline integration (903) is intentionally minimal — wire existing working code into new CLI commands, don't redesign it. That's Initiative 100's job.
- Squadron (~/source/repos/manta/squadron/) is the reference implementation for CLI, config, logging, and provider patterns. Structural replication, not domain logic.
