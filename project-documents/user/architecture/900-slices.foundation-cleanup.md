The python rules include test code in type checking specifically *because bugs in tests can mask bugs in code* — borne out on 2026-07-27, when a defect **in a test** (`test_cagg_freshness.py` froze the wall clock by monkeypatching a name that `_evaluate` had bound as an import-time default) silently disabled a freshness assertion and surfaced only when the fixture date aged past a threshold and broke the suite on a calendar boundary. Extend `files` to cover `test/` and drive that to zero too.
- **Strictness.** The block sets only `python_version` and `ignore_missing_imports`. A non-strict zero is a hollow number against a rule that calls zero errors a merge blocker, and enabling strict afterward reopens the debt immediately. **Ratchet within this slice** (PM ruling): reach zero non-strict first, then turn strict flags on incrementally and clear each wave, so the slice ends genuinely strict-clean rather than nominally clean. Expect the count to grow substantially when strict lands — that growth is in scope, and re-estimating effort once its true size is known is expected rather than a scope breach.

Verifiable: `uv run --extra dev ruff check src/ test/` reports zero violations; mypy passes over **both** `src/` and `test/` with the strict flags this slice lands; all per-subpackage test suites pass unchanged; the F821 code paths are exercised by at least a smoke test or documented as dead code and removed. [ ] **(910) Schema-Change Transparency and Confirmation** — An operator upgrading `mt` needs to know *before* running anything whether it will alter production database structure, and how severely. Today it cannot be known without reading SQL: migration records are `{id, description, sql}` ([market/schema/migrations/minute.py](../../../src/manta_trading/market/schema/migrations/minute.py)) with no impact classification, so in `mt data migrate status` a bare `CREATE TABLE` and a rewrite of the 4.4-billion-row `minute_ohlcv` hypertable render identically; and `mt data migrate apply` ([cli/commands/data.py:177](../../../src/manta_trading/cli/commands/data.py)) takes no dry-run, no plan preview, and no confirmation — it simply applies everything pending. **Scope:** (1) add an impact classification to the migration record as an enum (additive / rewrite / destructive) per the no-scattered-comparison-values rule, never a bare string, with optional operator notes carrying the concrete cost ("rewrites `minute_ohlcv`, ~4.4 B rows"), backfilled across the existing chain in both tracks; (2) render impact alongside description in `mt data migrate status` so the preview answers "how bad is this" without opening source; (3) give `mt data migrate apply` a plan-then-confirm gate — print the full pending plan, require explicit confirmation when any pending migration is non-additive, `--yes` for automation, `--dry-run` for inspection — and mirror the gate in `mt data init`, which shares the same apply path; (4) a version-skew guard so that when the installed build expects migrations the database has not applied, commands depending on the new schema fail naming the gap rather than surfacing a raw SQL error. This generalizes the requirement so it holds for every future release, not only the 908 cutover. Verifiable: unit tests assert the confirmation gate blocks a non-additive plan without `--yes` and passes an additive one; `--dry-run` applies nothing (asserted against migration state before and after); every migration in both tracks carries a classification; the skew guard's message is asserted to name the missing migration ids. Dependencies: none. Risk: Med (touches the schema runner every deployment depends on). Effort: 2/5

[x] **(912) Daemon Cycle Correctness — Data-Driven Daily Work Determination** — Closes GitHub issues [#7](https://github.com/manta-digital/trading-data/issues/7) and [#6](https://github.com/manta-digital/trading-data/issues/6), which are the same ~40 lines of `runner.py` and must be fixed together. **#7:** the daily cycle decides it has work from `RunnerState.last_daily_cycle_start_utc`, a field that records a *start* and lives only in memory. [runner.py:355-357](../../../src/manta_trading/data/acquisition/daemon/runner.py) stamps it *before* the `try:` around `_run_daily_cycle`, so a pass that dies partway — SIGTERM between symbols, an exception, an interrupted session — has already marked the UTC day done and `daily_cycle_due` returns `False` for the rest of it, silently and with no retry. That the field is also in-memory ([runner.py:112](../../../src/manta_trading/data/acquisition/daemon/runner.py)) masks the defect: every restart re-runs a full pass unconditionally, so operators only ever observe the recovery path. Observed on prod 2026-08-03 — a pass interrupted partway through the alphabet was recovered by an operator restart, not by the daemon. The minute cycle already has the right model: `minute_cycle_due` gates only on cadence and derives remaining work from `data_gaps` inside the cycle, so interruption and restart are self-healing. **Scope:** (1) derive the daily work list from the durable per-symbol truth already written by both daily paths — `acquisition_state.last_attempt_ts` relative to the current pass boundary — so an interrupted pass resumes at exactly the symbols it did not reach; (2) demote the day-timer to a busy-loop cadence guard, renaming the field to `last_daily_cycle_end_utc` and stamping it *after* the cycle returns, mirroring minute; (3) surface scope members the cycle cannot act on (no resolvable trading calendar, [daily.py:261-267](../../../src/manta_trading/data/acquisition/daemon/daily.py)) as an explicit un-actionable count rather than letting a derived work list either drop them silently or retry them forever — the interaction with #4, not a fix for it; (4) **#6:** distinguish "no cycle due yet" from "scope drained" in the `--stop-when-done` exit path via an enum, naming the next due time, and let a `--stop-when-done` run satisfy a cadence gate by sleeping rather than exiting on it — the case that made a scoped run launched at 00:13 UTC exit instantly claiming completion, having fetched nothing; (5) **#6 secondary:** split `LATE_BAR_GRACE_PERIOD` (documented as an offset from `session_close_utc`, applied in `runner.py` as an offset from UTC midnight — two concepts sharing one value by coincidence) into a distinct `DAILY_CYCLE_START_OFFSET`, per the single-definition-site rule. This slice is the maintenance band's home for daemon-cycle correctness; similar issues discovered in the same scope may be folded in. Verifiable: unit tests assert an interrupted pass resumes at the unreached symbols within the same UTC day; that a completed pass does not re-run; that the cadence guard prevents busy-looping when no work is actionable; that the exit message distinguishes both idle reasons and names the next due time; and that both constants exist independently with their own uses. Explicitly excludes assigning calendars to the 906 instruments (#4), any change to the minute path, and the AlphaVantage-era `data/acquisition/daily/freshness.py`. Dependencies: none. Risk: Med (the daemon runs continuously on prod; a work-determination bug either idles the pipeline or re-triggers billable bulk EOD calls every cadence tick). Effort: 3/5

[x] **(913) Least-Privilege Database Roles — Make Credential Leaks Non-Destructive** — The 2026-08-04 incident ([notes](../notes/2026-08-04-prod-metadata-truncation-incident.md)) destroyed six production tables because a single credential carries every privilege: the URL a test fixture received could `TRUNCATE ... CASCADE` and `DELETE` from the migration ledger. Every control added since is *procedural* — the static ratchet guards (`test/_prod_url_guard.py`), the runtime scrub in `test/conftest.py`, and the additive-allowlist runner (`scripts/run_tests.py`) — and each depends on code or a caller doing the right thing. This slice makes the blast radius structural: with DML-only application credentials, the same leak dies on `permission denied` and destroys nothing, which is the one control that holds even when the tooling is bypassed entirely. It is the outstanding half of the `sql.md` "Production Database Protection" rule set, whose first bullet ("Split connection roles") is the only one not yet enforced by the server. **Scope:** (1) define the role split — an application role holding DML only (no `TRUNCATE`, a separately grantable privilege; no DDL, no ownership, read-only on `schema_migrations`) and a distinct migration/maintenance role holding DDL, supplied only when doing that work; (2) provision both roles and their grants as a reviewable, idempotent, re-runnable artifact covering existing *and* future tables (default privileges), applied to `trading` on .144; (3) introduce a distinct settings key for the maintenance URL so the daemon, API server, and CLI read paths run as the application role while `mt data migrate apply` / `mt data init` / rechunk and restore tooling take the maintenance URL from an explicit caller argument, never ambient environment; (4) verify the negative case — assert the application role *cannot* TRUNCATE, DROP, or write the ledger — as a test, so the protection cannot silently regress the way an absent guard did. Sequencing note: the privilege split will surface any read path that quietly relied on ownership, so it wants a full daemon + API + integration-tier pass before the old credential is retired; keep the superuser URL available for rollback until that pass is green. Verifiable: the application role raises `permission denied` on TRUNCATE/DROP/ledger-write against `trading`, asserted by test; migrations apply successfully under the maintenance role and fail under the application role; the daemon completes a full daily and minute cycle, and all API endpoints serve, under application-role credentials; the grant artifact is idempotent across a second run. Dependencies: none. Risk: Med (a missing grant breaks a production read path; mitigated by the pre-cutover pass and retained rollback credential). Effort: 3/5

16. [x] **(915) Backup and Restore Procedures** — The project has **no backup procedure and no tested restore path**. Production backup today is an operator manually copying the PostgreSQL data directory to an external drive; on 2026-08-10 that copy was taken while the server was *running*, which produces a torn, unrestorable image — `cp` reads a 150 GB directory over many minutes while Postgres writes 8 KB pages and WAL continuously, so the copy corresponds to no single instant and carries no crash-recovery guarantee. It usually restores anyway, which is precisely the hazard: it fails on the copy where an index page was mid-split, discovered during an emergency. Measured on prod 2026-08-11: `wal_level=replica`, **`archive_mode=off`**, no archive command, single `pg_default`/`pg_global` tablespace, `trading` at 150 GB. With archiving off there is no point-in-time recovery at all — recovery granularity is "whenever someone last remembered to copy," and the gap between the last copy and a failure is unrecoverable by construction. This is the outstanding action item from the 2026-08-04 incident ([scoping notes](../notes/2026-08-04-prod-db-guardrails-scoping.md#backup-exposure-from-the-incident-notes-action-item)), whose priority table is this slice's requirements input: `minute_ohlcv` (4.4 B rows) is **priority 1** — re-derivable from EODHD *in principle* but not in practice, costing quota and weeks of pulling — followed by `daily_ohlcv`, then `acquisition_state`, whose loss forces a mass re-pull. Sibling to 913: that slice made a credential leak non-destructive, this one makes destruction survivable. **Scope:** (1) enable WAL archiving on .144 (`archive_mode`, an archive command, retention) so point-in-time recovery exists, provisioned as a reviewable idempotent artifact in the `scripts/provision_roles.sql` mould rather than hand-typed onto the host, and noting the restart archiving requires; (2) adopt `pg_basebackup -Ft -z -Xs` as the base-backup mechanism — it takes a checkpoint and streams the WAL needed to make the copy self-consistent, so it is valid against a *live* server and needs no maintenance window, unlike the current file copy; (3) choose and document an offsite target with a tradeoff table in the design (Backblaze B2, S3 Glacier Deep Archive / Glacier IR, GCS Archive — compared on monthly cost at ~150 GB, retrieval latency, retrieval and egress fees, and **minimum storage duration**, which is the term that quietly dominates when backups are re-pushed after large migrations; B2's no-retrieval-fee/no-minimum-duration shape is the current front-runner but the design decides), plus how the credential is supplied without ever entering the repo; (4) a two-tier cadence separating what cannot be re-derived from what merely costs money to re-derive — a small frequent logical dump of the metadata tables the 2026-08-04 incident actually destroyed (`instruments`, `acquisition_state`, coverage, calendars — megabytes, cheap enough to run nightly) alongside an infrequent full base backup; (5) an `mt`-level command or script wrapping base-backup → verify → offsite sync so the procedure is one invocation rather than remembered steps, taking its DB URL from an explicit caller argument per the maintenance-tooling rule and using the 913 maintenance credential; (6) **a restore drill executed and documented** — restoring into a throwaway target and verifying content, not catalog presence, per the `sql.md` rule that a derived object interrupted mid-incident is presumed damaged. An untested restore path is not a backup. Deliverables include a runbook alongside `cagg-maintenance-pausing.md`. Explicitly excludes replication/standby (a different problem — availability, not recoverability) and any change to `restore_metadata.py`'s ledger-replay logic, whose known boundary is documented in the scoping notes. Verifiable: `archive_mode=on` with WAL segments landing in the archive, asserted from the catalog; a base backup completes against the live server with the daemon running; the offsite copy is verified by checksum rather than assumed from a clean exit; and the restore drill brings up a working cluster whose row counts for the priority-1 tables match the source. Dependencies: [913]. Risk: Med (archiving changes production server config and requires a restart; an archive command that silently fails fills `pg_wal` and can take the server down, so the design must cover archive-failure monitoring). Effort: 3/5

The suite races itself: the fixture's `DROP DATABASE` at teardown collides with the next test creating its database and applying the migration chain, at `DROP MATERIALIZED VIEW IF EXISTS minute_coverage` ([minute.py:2140](../../../src/manta_trading/market/schema/migrations/minute.py)). The window exists because that migration runs without a transaction — deliberately, since it drops and recreates continuous aggregates — so no lock is held across the sequence. **Measured on the dedicated host:** teardown drops enabled, 4 of 6 runs failed; teardown suppressed, 0 of 6; one test per pytest process, 0 of 10. Ruled out: production activity, the TimescaleDB scheduler racing within one database, and parallel execution (no parallel runner is installed). **A fix was attempted and is preserved as a patch** — defer all drops to session end, with a session-start sweeper for interrupted runs. It removes the races completely (zero across a full 540-second tier) but breaks `test_policy_advances_head.py`, which waits on the real background scheduler and reports `last_successful_finish=None`; attribution confirmed by running the same pair with and without the patch. A refinement deleting each retired database's jobs did not rescue it. **First thing to check:** that refinement swallows every database error so teardown cannot fail a test, so it may never have executed — the worker-starvation theory may be untested rather than disproven. Verifiable: five consecutive full integration runs with zero races, `test_policy_advances_head.py` 9/9 *within* a full run rather than only in isolation, and the rest of the pass/fail set unchanged. Dependencies: []. Interfaces: [905, 907, 917]. Risk: Low. Effort: 2/5.

## Future Work

1. [ ] **Config path constants**: `~/.config/manta-trading/config.toml` and `.manta-trading.toml` are bare literals at [config/manager.py:18,23](../../../src/manta_trading/config/manager.py). The values are correct and must not change — they key to the `mt` product identity, not the distribution name, and hold user data — but lifting them to named constants would make that decoupling explicit rather than coincidental, and prevent a future rename dragging them along. Raised as F001 in the slice 908 design review.

2. [ ] **Let the test suite use production's real role names**: `scripts/provision_roles.sql` documents that a test run "MUST pass throwaway role names — otherwise it mutates the very roles production depends on," because `pg_authid` is cluster-wide. Slice 917 moved the test databases to a separate cluster, so that hazard is gone and the suite could exercise the *real* role names — a fidelity gain, since the test would then run the exact invocation production runs rather than a parameterised variant. Left alone by 917 deliberately: the parameters are harmless once the cluster is separate, and changing slice 913's privilege suite was not that slice's work. Related: two stale `t913_*` roles and three orphaned `mt_test_*` databases remain in production's catalog, residue from interrupted runs before the move; removing them is a Project Manager decision, not a code change.
3. [ ] **A single-machine path for other users of this repository**: the test-database setup assumes two database-capable machines, which most people cloning this project will not have. The answer is cheap and already written down — a second PostgreSQL cluster on the same host is what a one-machine user would do, and it is preserved in the git history of [917-slice.dedicated-test-database-cluster-stop-sharing-a-catalog-with-production.md](../slices/917-slice.dedicated-test-database-cluster-stop-sharing-a-catalog-with-production.md), whose first version specified exactly that. Everything downstream of the cluster is identical either way: role provisioning, the `MT_TIMESCALE_TEST_URL` indirection, and the guards that refuse a production-pointing URL. Only the cluster's location differs. Worth writing into the README or the test-cluster runbook before this repository has outside users.

## Notes

- Slice 900 is the largest because it establishes both CLI and config systems together — they're co-dependent (CLI needs config for setup, config needs CLI for management commands). Splitting them would create circular dependencies.

- The daily pipeline integration (903) is intentionally minimal — wire existing working code into new CLI commands, don't redesign it. That's Initiative 100's job.
- Squadron (~/source/repos/manta/squadron/) is the reference implementation for CLI, config, logging, and provider patterns. Structural replication, not domain logic.
