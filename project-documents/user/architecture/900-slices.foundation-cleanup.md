## Migration / Refactoring Slices

4. [x] **(903) Deprecated Code Removal and httpx Migration** — Delete `market/deprecated/` directory and all imports from it. Remove old CLI entry points (`ohlc.py` direct invocation, `newsoptions.py`). Replace aiohttp with httpx in AlphaVantage client. Wire existing daily pipeline (`marketdb.py`, `marketservice.py`) into new CLI as `mt data daily` subcommands. Dependencies: [900, 902]. Risk: Med. Effort: 3/5

5. [ ] **(905) Lint and Type-Checker Debt Remediation** — Slice 166's code review landed the mandated `[tool.ruff]`/`[tool.ruff.lint]` config (`E,F,W,I,UP,BLE,ASYNC,B`) and a `[tool.mypy]` block in `pyproject.toml`; activating it exposed **1,730 pre-existing violations across `src/` and `test/` (752 autofixable)** that had never been mechanically gated (re-measured 2026-07-27: **1,706 ruff, 739 autofixable** — the drift is slices closing since). This slice drives that count to zero so the config gates all code, not just new code by review convention. Scope: (1) apply the ruff autofixes and verify no behavior change (per-subpackage test runs); (2) manually triage the remainder — **note that some findings are latent runtime bugs, not style**: the sweep includes `F821` undefined names in `cli/commands/data.py` (e.g. `datetime`, `psycopg` referenced in code paths where they are not imported — a `NameError` waiting on those paths), plus `F401` unused imports, `E402` late imports, `E501` line lengths, and any `BLE` blind-except violations, each fixed or explicitly `noqa`'d with an inline justification per the exception-handling rules; (3) sweep `raise ... from exc` (B904) across the legacy handlers noted in the 166 review; (4) drive `uv run --extra dev mypy` to zero — **97 errors across 20 files** as measured 2026-07-27, worst offenders `market/csv_export_service.py` (28), `cli/commands/provider.py` (23), `cli/commands/data.py` (15); (5) **widen and tighten the mypy gate**, see below. Latent-bug fixes (F821 class) get their own commit(s) with a note distinguishing them from mechanical style fixes.

**Type-checker decision and gate scope (PM, 2026-07-27).** The project stays on **mypy**, not pyright — the python rules say "`pyright` (preferred) **or mypy**", and `pyproject.toml` records the mypy choice as a deliberate slice-166 code-review resolution. Switching tools mid-cleanup would re-triage the same debt twice for no gain; revisit after this slice, not during it. Two real gaps in the gate as currently configured, both this slice's to close:

- **Scope.** `[tool.mypy] files` is `["src/manta_trading"]`, so `test/` is unchecked. The python rules include test code in type checking specifically *because bugs in tests can mask bugs in code* — borne out on 2026-07-27, when a defect **in a test** (`test_cagg_freshness.py` froze the wall clock by monkeypatching a name that `_evaluate` had bound as an import-time default) silently disabled a freshness assertion and surfaced only when the fixture date aged past a threshold and broke the suite on a calendar boundary. Extend `files` to cover `test/` and drive that to zero too.
- **Strictness.** The block sets only `python_version` and `ignore_missing_imports`. A non-strict zero is a hollow number against a rule that calls zero errors a merge blocker, and enabling strict afterward reopens the debt immediately. **Ratchet within this slice** (PM ruling): reach zero non-strict first, then turn strict flags on incrementally and clear each wave, so the slice ends genuinely strict-clean rather than nominally clean. Expect the count to grow substantially when strict lands — that growth is in scope, and re-estimating effort once its true size is known is expected rather than a scope breach.

Verifiable: `uv run --extra dev ruff check src/ test/` reports zero violations; mypy passes over **both** `src/` and `test/` with the strict flags this slice lands; all per-subpackage test suites pass unchanged; the F821 code paths are exercised by at least a smoke test or documented as dead code and removed. Note for slice 907: its pipeline runs `ruff → mypy → pytest`, so whatever gate this slice lands must be mirrored there. Dependencies: [166]. Risk: Med (BLE and F821 triage touches many files; behavior must be preserved except documented latent-bug fixes; the strict ratchet's true size is unknown until non-strict zero is reached). Effort: 3/5

6. [ ] **(906) `mt data` CLI Module Decomposition** — `cli/commands/data.py` is 3,371 lines, >10x the ~300-line guideline, because eight Typer sub-apps (`data` root, `caggs`, `ca`, `instruments`, `lists`, `daemon`, `migrate`, `calendars`) were appended to one module rather than each getting its own. Flagged as F009 in the slice 163 review and deferred; slice 168's review established that over-guideline length is only excusable when the excess is not code — `data.py`'s excess is executable code, so it isn't. Split into a `cli/commands/data/` package, one module per sub-app plus `_shared.py` for the cross-group helpers, with `__init__.py` assembling the Typer tree and re-exporting `data_app` so `cli/app.py` is untouched. Generalizes the existing `universes.py` precedent, which already lives outside the module and is attached via `add_typer`. Strictly behavior-preserving: no signature, help-text, output-format, or exit-code changes, verified by diffing pre/post `--help` captures for all nine sub-apps. Pushing SQL and formatting logic down out of the oversized command bodies (`data_pull` 244 lines, `caggs_status` 202, `data_get` 192) is explicitly follow-on work, not this slice. Depends on 905 so that slice's `F821` latent-`NameError` findings in this exact file are fixed while the code is still in one place, rather than scattered across ten new modules mid-triage. Dependencies: [905]. Risk: Low (mechanical move; live-daemon entry point `daemon run` requires a real prod invocation to verify). Effort: 2/5

7. [ ] **(907) CI Pipeline and Load-Test Gating** — The repo has **no CI**; `.github/workflows` does not exist, so ruff, mypy, pytest, and the `test/load/` NFR tier all run only when someone remembers to locally. Slice 146 added two load tests gated on `MT_RUN_LOAD_TESTS=1` whose docstrings say "CI must enable" — nothing ever did, so those NFR assertions have never run automatically. Slice 167's task review (F002) caught the identical claim being made again for its sub-second `data_status` load test; the PM ruled the CI work out of 167 and into this chore rather than ship a second NFR with an aspirational gate. Scope: workflow config running ruff → mypy → pytest per-subpackage on push/PR — **mypy must run over both `src/` and `test/` with whatever strict flags slice 905 lands** (905 widens and ratchets that gate; CI mirroring the old `src/`-only non-strict invocation would silently under-enforce it) — plus a load-tier job setting `MT_RUN_LOAD_TESTS=1` so the 146 and 167 NFRs get a real gate; decide per-suite whether DB-dependent tests get an ephemeral service container or a recorded skip; quarantine the known pre-existing failure baseline (2 failures + 12 live-DB errors) so a green run means something; retire the "CI must enable" docstrings. Must respect the broken whole-`test/` collection (missing `__init__.py` — per-subpackage invocation) and must never be able to reach the production DB at 192.168.1.144, where the daemon runs continuously. Explicitly excludes new tests, threshold changes, and fixing the baseline failures. Dependencies: [905]. Risk: Low (additive; no production code paths touched — the risk is a pipeline that goes red on day one and gets ignored, which the baseline quarantine addresses). Effort: 2/5

## Integration Work

8. [x] **(904) Packaging and Version** — Completed incrementally across slices 900–903: `uv.lock` committed, `mt` entry point wired, `mt --version` implemented, `pip install -e .` and `uv sync` verified. No standalone slice design needed. Dependencies: [903]. Effort: 0/5

9. [x] **(908) PyPI Publication** — `mt` cannot be installed except by cloning the repo ([README.md](../../../README.md)), and an installed copy has no way to learn a newer version exists: `v0.5.0` is tagged but `gh release list` is empty, and `mt --version` reads `importlib.metadata` without ever consulting a registry. PyPI holds `manta-trading` at `0.0.1` ("Manta Trading - placeholder package"), a name reserved for a future full product rather than this data package. **Scope:** (1) rename the *distribution* to `manta-trading-data` (verified unclaimed on both PyPI and TestPyPI 2026-08-01; the import package `manta_trading` deliberately stays put, renamed separately and invisibly by 911) and lift the hard-coded `importlib.metadata.version("manta-trading")` lookup at [cli/app.py:36](../../../src/manta_trading/cli/app.py) into a constant, since that literal fails *silently* on rename — the `PackageNotFoundError` branch already falls back to `"dev"`; (2) add the repo's first `.github/workflows/ci.yml` with a tag-gated publish job modelled on `squadron/.github/workflows/ci.yml` — `permissions: id-token: write`, `uv build`, then `pypa/gh-action-pypi-publish` at TestPyPI (non-blocking rehearsal) and PyPI, using the trusted publishers the PM configured on both sites 2026-08-01 (`manta-digital` / `trading-data` / `ci.yml`, no environment — the workflow must carry no `environment:` key or the OIDC claim fails); naming it `ci.yml` lets 907 add lint/type/test to the same workflow later, and keeping those jobs out means releases do not wait on 905's lint sweep; (3) publish 0.6.0 and adopt `gh release create` per tag, backfilling v0.5.0, so watchers and the releases feed get a real notification channel. Explicitly excludes anything touching .144 — production continues to run from its checkout, and migrating it onto a published artifact is Future Work below, to be designed on its own terms. Verifiable: `uv tool install manta-trading-data` into a clean environment yields a working `mt` whose `--version` matches the published version (a `dev` result means the constant and the distribution name disagree); `uv tool install --upgrade` is demonstrated between two published versions; `gh release list` shows v0.5.0 and v0.6.0; publishing uses no credential stored in the repo or in GitHub secrets. Dependencies: [904]. Risk: Low. Effort: 2/5

10. [x] **(909) `mt update` Self-Update Command** — Once 908 makes releases installable, an installed user still has no in-tool way to discover or apply one; `mt --version` reads `importlib.metadata` and never consults a registry. Port the shape proven by `cf update` (~187 lines, `context-forge/packages/cli/src/commands/update.ts`): query the latest published version, compare, detect how the tool was installed, and shell out to the matching upgrade command. **Scope:** (1) fetch `https://pypi.org/pypi/manta-trading-data/json` → `info.version` with a bounded timeout, returning nothing rather than raising on any failure (network, non-200, malformed) so a registry outage never breaks the command; (2) compare with `packaging.version` — declared as an explicit dependency, not relied on transitively — rather than hand-rolled string splitting; (3) detect install method and auto-upgrade only the blessed `uv tool install --upgrade manta-trading-data` path, printing the correct command for pipx/pip-user installs and refusing outright on an editable or source-checkout install (the state every developer machine is in today); (4) `--json` as a pure query with no side effects, `--yes` for non-interactive use, and non-TTY-without-`--yes` reporting rather than acting. **The command must never touch the database.** After a successful code upgrade it reports the pending-migration count and points at `mt data migrate status`; that check is best-effort and a failure to reach the database must not fail the update. The registry call happens only when the command is invoked — never at CLI startup. Verifiable: unit tests cover up-to-date, update-available, unreachable-registry, and each install-method branch with the upgrade call mocked; `--json` output is asserted side-effect-free; a real end-to-end upgrade is performed between two published versions. Dependencies: [908]. Risk: Low. Effort: 2/5

11. [ ] **(910) Schema-Change Transparency and Confirmation** — An operator upgrading `mt` needs to know *before* running anything whether it will alter production database structure, and how severely. Today it cannot be known without reading SQL: migration records are `{id, description, sql}` ([market/schema/migrations/minute.py](../../../src/manta_trading/market/schema/migrations/minute.py)) with no impact classification, so in `mt data migrate status` a bare `CREATE TABLE` and a rewrite of the 4.4-billion-row `minute_ohlcv` hypertable render identically; and `mt data migrate apply` ([cli/commands/data.py:177](../../../src/manta_trading/cli/commands/data.py)) takes no dry-run, no plan preview, and no confirmation — it simply applies everything pending. **Scope:** (1) add an impact classification to the migration record as an enum (additive / rewrite / destructive) per the no-scattered-comparison-values rule, never a bare string, with optional operator notes carrying the concrete cost ("rewrites `minute_ohlcv`, ~4.4 B rows"), backfilled across the existing chain in both tracks; (2) render impact alongside description in `mt data migrate status` so the preview answers "how bad is this" without opening source; (3) give `mt data migrate apply` a plan-then-confirm gate — print the full pending plan, require explicit confirmation when any pending migration is non-additive, `--yes` for automation, `--dry-run` for inspection — and mirror the gate in `mt data init`, which shares the same apply path; (4) a version-skew guard so that when the installed build expects migrations the database has not applied, commands depending on the new schema fail naming the gap rather than surfacing a raw SQL error. This generalizes the requirement so it holds for every future release, not only the 908 cutover. Verifiable: unit tests assert the confirmation gate blocks a non-additive plan without `--yes` and passes an additive one; `--dry-run` applies nothing (asserted against migration state before and after); every migration in both tracks carries a classification; the skew guard's message is asserted to name the missing migration ids. Dependencies: none. Risk: Med (touches the schema runner every deployment depends on). Effort: 2/5

12. [ ] **(911) Import-Package Rename to `manta_trading_data`** — Deferred half of the 908 naming decision. With the distribution published as `manta-trading-data` but the import package still `manta_trading`, this package would collide on disk with the future full product if that ever ships the same import root; the PM's decision is to rename rather than reserve a different root for the future package. Purely internal — the distribution name, the `mt` entry point, and every user-facing surface are unchanged, so an installed user upgrading across this version notices nothing. **Scope:** mechanical move of `src/manta_trading/` → `src/manta_trading_data/` with all imports across `src/` and `test/` updated, the `[project.scripts]` entry point target adjusted, and the distribution-name constant introduced in 908 left untouched. Strictly behavior-preserving: no signature, output-format, or exit-code changes. Best sequenced after 906 splits `cli/commands/data.py`, to avoid renaming imports in a 3,371-line module that is about to be decomposed. Verifiable: all per-subpackage test suites pass unchanged; `grep -r manta_trading\\b` over `src/` and `test/` returns nothing outside the new name; a clean `uv tool install` of the resulting build produces a working `mt` at the same version. Dependencies: [908]. Risk: Low. Effort: 2/5

13. [ ] **(912) Daemon Cycle Correctness — Data-Driven Daily Work Determination** — Closes GitHub issues [#7](https://github.com/manta-digital/trading-data/issues/7) and [#6](https://github.com/manta-digital/trading-data/issues/6), which are the same ~40 lines of `runner.py` and must be fixed together. **#7:** the daily cycle decides it has work from `RunnerState.last_daily_cycle_start_utc`, a field that records a *start* and lives only in memory. [runner.py:355-357](../../../src/manta_trading/data/acquisition/daemon/runner.py) stamps it *before* the `try:` around `_run_daily_cycle`, so a pass that dies partway — SIGTERM between symbols, an exception, an interrupted session — has already marked the UTC day done and `daily_cycle_due` returns `False` for the rest of it, silently and with no retry. That the field is also in-memory ([runner.py:112](../../../src/manta_trading/data/acquisition/daemon/runner.py)) masks the defect: every restart re-runs a full pass unconditionally, so operators only ever observe the recovery path. Observed on prod 2026-08-03 — a pass interrupted partway through the alphabet was recovered by an operator restart, not by the daemon. The minute cycle already has the right model: `minute_cycle_due` gates only on cadence and derives remaining work from `data_gaps` inside the cycle, so interruption and restart are self-healing. **Scope:** (1) derive the daily work list from the durable per-symbol truth already written by both daily paths — `acquisition_state.last_attempt_ts` relative to the current pass boundary — so an interrupted pass resumes at exactly the symbols it did not reach; (2) demote the day-timer to a busy-loop cadence guard, renaming the field to `last_daily_cycle_end_utc` and stamping it *after* the cycle returns, mirroring minute; (3) surface scope members the cycle cannot act on (no resolvable trading calendar, [daily.py:261-267](../../../src/manta_trading/data/acquisition/daemon/daily.py)) as an explicit un-actionable count rather than letting a derived work list either drop them silently or retry them forever — the interaction with #4, not a fix for it; (4) **#6:** distinguish "no cycle due yet" from "scope drained" in the `--stop-when-done` exit path via an enum, naming the next due time, and let a `--stop-when-done` run satisfy a cadence gate by sleeping rather than exiting on it — the case that made a scoped run launched at 00:13 UTC exit instantly claiming completion, having fetched nothing; (5) **#6 secondary:** split `LATE_BAR_GRACE_PERIOD` (documented as an offset from `session_close_utc`, applied in `runner.py` as an offset from UTC midnight — two concepts sharing one value by coincidence) into a distinct `DAILY_CYCLE_START_OFFSET`, per the single-definition-site rule. This slice is the maintenance band's home for daemon-cycle correctness; similar issues discovered in the same scope may be folded in. Verifiable: unit tests assert an interrupted pass resumes at the unreached symbols within the same UTC day; that a completed pass does not re-run; that the cadence guard prevents busy-looping when no work is actionable; that the exit message distinguishes both idle reasons and names the next due time; and that both constants exist independently with their own uses. Explicitly excludes assigning calendars to the 906 instruments (#4), any change to the minute path, and the AlphaVantage-era `data/acquisition/daily/freshness.py`. Dependencies: none. Risk: Med (the daemon runs continuously on prod; a work-determination bug either idles the pipeline or re-triggers billable bulk EOD calls every cadence tick). Effort: 3/5

## Future Work

1. [ ] **Production deployment from a published artifact**: .144 installs by `git clone` into `/opt/manta-trading` + `uv sync`, and both systemd units hard-code that checkout (`WorkingDirectory=/opt/manta-trading`, `ExecStart=/usr/local/bin/uv run mt …`), so no package manager can upgrade it. Moving it onto the published package is worth doing eventually, but it is ops work with its own decisions and should be designed on its own terms rather than folded into a publication slice — the attempt to do so in 908 forced `uv tool install`, which targets interactive user tools, onto a `nologin` system account whose home directory *is* the checkout, and produced complexity out of proportion to the goal. Decisions to resolve when picked up: install shape for a service (a root-owned pinned venv with an absolute `ExecStart` is the conventional answer, and touches no user accounts), whether `/opt/manta-trading` is retained as a rollback path, and how migrations are sequenced around the restart. Related: [production-deploy.md](../runbooks/production-deploy.md) is first-install-only with no upgrade procedure at all, and is stale in two known places — a retired `--db all` flag on its migration step, and a clone URL predating the repo rename.
2. [ ] **Config path constants**: `~/.config/manta-trading/config.toml` and `.manta-trading.toml` are bare literals at [config/manager.py:18,23](../../../src/manta_trading/config/manager.py). The values are correct and must not change — they key to the `mt` product identity, not the distribution name, and hold user data — but lifting them to named constants would make that decoupling explicit rather than coincidental, and prevent a future rename dragging them along. Raised as F001 in the slice 908 design review.

## Notes

- Slice 900 is the largest because it establishes both CLI and config systems together — they're co-dependent (CLI needs config for setup, config needs CLI for management commands). Splitting them would create circular dependencies.
- Slice 903 carries medium risk because the deprecated code removal touches the main entry point and the httpx migration changes the HTTP layer. Both are well-scoped but affect working functionality.
- The daily pipeline integration (903) is intentionally minimal — wire existing working code into new CLI commands, don't redesign it. That's Initiative 100's job.
- Squadron (~/source/repos/manta/squadron/) is the reference implementation for CLI, config, logging, and provider patterns. Structural replication, not domain logic.
